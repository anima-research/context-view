# What a context view runs and checks

A context view runs the whole connectome-host, with its real agent-framework, context-manager, membrane and chronicle, through 77 scripted runs. It does this twice: once on the pull request's base, and once with its head merged onto the base. A stand-in answers for the model's API, Anthropic's, OpenAI's Responses API in P1's run, ChatGPT's Codex backend in P2's, Amazon Bedrock's in P3's, or the Chat Completions API as OpenAI documents it in P5's and as OpenRouter serves it in P4's, so no model is called and every answer is the same each time. Each run records every request the host sends, and is judged by the checks below. The comment then says which runs' records changed between the two, and which flags one side raised more times than the other.

The harness that does this is in `harness/`. Its `README.md` gives each check's exact rules, in "What each run's checks judge".

## What a view's comment rests on

The pull request's own code runs in the job that makes these records, so everything a view reports from its runs rests on that code acting in good faith. A view isn't a security check.

A view speaks only for its runs: a case of the change that none of them reaches doesn't show in its records.

Each run has one resident, since connectome-host runs one (`agents: [agentConfig]`), so a change to what residents sharing one slot are shown doesn't show in any run.

Some settings of the kv-unified solver reach nothing on the continuation at context-manager 0.25.0, so a change to what they govern doesn't show there: pinning the subtree engine, since an unpinned engine is the subtree engine until the label ceiling, which no continuation run reaches; turning the hysteresis certificate off, which by its doc can change a bucketed solve's choice but moved nothing in a run with it off; treeifying summaries over gaps and preserving them (`treeifyNonContiguousSummaries`, `preserveGapBearingSummaries`), which act only on a store that holds a summary over a gap, and none of these stores does; and measuring producible merges one at a time (`latentDemandMode: 'individual'`), which moves nothing on the continuation, by a run of C11h's settings one at a time. C11h sets the last two, and no setup sets the first three.

The host's `tuneOut.announce` decides whether the channel a tune-out of every channel but one excepts hears that scope open and close, a line agent-framework 0.33.0 posts to that channel. It's on unless a recipe turns it off, and no setup turns it off, so `H4/W1`'s `w1-keep` hears both lines, and its `false` reaches nothing.

A record writes a `wrote`, `removed` or `unreadable` line, a summary the host's store shows written or gone or a store read that failed, where the driver takes the host's compiles at a settle's end, after the last request the stand-in received before then. So such a line could sit on either side of a later request of its step, by where a settle ended, which nothing in the run decides. A settle ends only when the host's readout shows every agent ready, no deferred write, no compression tick in flight and no turn alive but one a provider hold keeps. A reader fork's summary can go unwritten, though, when its summariser answers after the fork has ended: agent-framework 0.33.0 withdraws the maintenance calls out on a context manager it's done with, as at a fork's end, and the withdrawn tick writes nothing. Such a summary appeared in each drive where the stand-in answered at once, and in none where the answer came 3 s late, after the fork had ended, even at `h5`, where the step's settle lasted past that answer: three drives of `H4b/W1` with every summariser request answered 3 s late each lacked two reader-fork summaries, one at `h4` and one at `h5`, which three unhurried drives wrote. Whether such a summary appears in the record is a race nothing in the run orders. The fork had already ended, and in those drives the resident's own store wrote the same summary at `h5` whether its answer came at once or late. Otherwise those drives, and three delayed drives of `C6h/W8/enforced`, listed each summary they wrote in the same batch, after the same requests, as the unhurried drives did. Besides that race, three kinds of request are made outside anything a settle waits for: the reply judge's, the suppression review's, and connectome-host's session naming, which it starts at the third external message and doesn't wait for. The others are inside it: the retrieval module's concept and relevance requests are made as a turn starts (agent-framework's `beginAgentTurn` gathers module context while the turn holds its token), and a bare `/newtopic`'s transition summary is answered before the command reports done, which the driver waits for. In a whole view's 152 records at this harness, 0 of their 4,318 such lines sit in a step that asks the judge, the review or for a name. A workload that makes one of those three requests in a step that compresses would be exposed, so its builder checks its records for such a line. A compile that sent no request is placed so that no settle's end moves it (`harness/README.md`).

A record holds what each request carried, as its text and hashes, not how many tokens it held or what it would cost. Beside the records, each run's result sums its requests' tokens by kind of request, as the stand-in counted them by its model of each provider's published caching and token rules: the tokens each request sent, how many of them were read from the cache and how many written to it, its output, and the thinking blocks the stand-in dropped. The comment gives the agents' requests' figures, subagents' included, base beside head, above the fold, and each run whose figures moved in a fold. They're the stand-in's model, not a measurement.

A record names a message by its canary, or by the summaries it comes from, and beside that name writes what the message carries besides the fixture's own words, such as a strategy's header or note, the line the host stores ahead of a channel message, a cut, or a recall pair's question. A frame that is the same at every compile of its message, and holds no number, is written once, on a form line. Two parts of a request it doesn't write out. What a continuation round adds is named by its canaries alone, so the rest shows only in the round's body hash. And a summariser request's slice is named by its canaries too, since what a resident reads of it is the summary, which the record writes whole.

On a model that thinks only when asked, such as Claude Opus 4.6, H1's and H3's model, the stand-in answers a script's thinking whether or not the request asks for thinking, where the provider sends none unasked. So a change that stops or starts asking for thinking on such a model doesn't show in what the stand-in sends back.

In P1's and P2's runs, on OpenAI's Responses API and ChatGPT's Codex backend, a record holds each item a request sent by its own digest. A reasoning item's content and a compaction item's are opaque, so a change to them shows as an item's digest moving, with no text to read. The values membrane draws at random on the Codex backend, its cache key and `session_id` header, are written by their shape and numbered by first appearance in the run, so they make neither two arms nor a run's self-check differ, while a change in which requests share a key does. In P5's runs, on the Chat Completions API, a record holds each message a request sent by its own digest, the system prompt among them, and an image in a tool result goes as membrane's text in its place, so a change to the image itself shows nowhere. P3's runs, on Amazon Bedrock, are recorded as the Messages API's, with the Bedrock model and route in each head. `harness/README.md`'s "Reading a record" says how each line reads.

Where records differ, a model reads the differences and writes the account at the top of the comment. Code checks that the account covers every difference between the records of the runs that could be compared, and that its quotes are copied from the records. It also checks that the account's prose has no numbers of two or more digits, decimals or hashes, no counts of runs, steps, compiles, requests or rounds, and none of the records' notation. The comment gives its own counts of runs, changes and steps. Nothing checks whether its sentences are true.

## Which of the change's source lines ran

Each run drives the head twice: once recording, and once with recording off for the self-check. Each drive keeps its stores under a directory name of the other's length made of lowercase ASCII letters, since a store's path reaches requests, and both token counters a run meets count a text by its length at a rate set by its characters' classes: context-manager's estimate (`defaultTokenEstimator`, `message-store.ts` 2381–2396 at 0.25.1, counting punctuation and any character above 126 as dense) and the stand-in's (`textTokens` in `harness/lib/standin/tokens.ts`, with a base64 test that reads lowercase apart from uppercase). A path one name longer once moved a cache marker by a block, since context-manager's kv-unified folding places its markers at thirds of the history's estimated tokens, and the self-check said "differs" where the bodies held the same content. A change to either counter can make the self-check say "differs" from the paths alone, so a reader of such a view looks there first. The second drive is the run's profiled drive. Every host it starts, a profiled host, runs under Bun's inspector with its control-flow profiler on. At each host's exit, the harness reads which code ran. The change's source lines are the lines it adds or edits under `src/`, beside the hunks there that only delete lines. A file it deletes whole leaves no line on the head to read. The comment names the source lines that ran in no profiled drive and the source files no profiled host loaded. Or it says that every source line that maps to code ran in at least one, or why it couldn't tell. The comment can cut a list or a reason, or count lines it doesn't name. Then a fold below it holds every changed source line and deletion not seen to run, file by file. For each line or deletion the comment couldn't tell about, the fold gives the reason. A reason longer than a comment can hold is cut there. The recording drive isn't profiled, so no record changes. The self-check shows anything profiling changed in the request bodies the host sent. The self-check masks values that vary from run to run anyway, such as thinking signatures. `harness/README.md`'s "Which of a change's lines ran" gives the exact rules.

- "Ran" means some profiled host executed code mapped from the line. Code that only the recording drive runs, such as the test module's own reads of the store, doesn't count. "Ran" isn't "tested": a line can run without the inputs that make its change matter. Only whether it ran is read, not how often.
- Each view reads one profiled drive of each run. Some code runs or not by timing, such as a timer or the order of async events. A changed line on such a path can run in one view and not in another view of the same head.
- A line reads "ran in no profiled drive" only when every profiled host was read and nothing unprofiled could have run it. Otherwise it reads "couldn't tell", with the reason. These reasons cover every line not seen to run:
  - a host that wasn't read;
  - a profiled drive that failed partway, couldn't run or started no host;
  - a run that couldn't run;
  - a share whose reads didn't come home;
  - a worker or child process whose code the read can't follow;
  - a built script of the changed package with no source map, loaded by a host, since it may hold a copy of any file's code;
  - a loaded script the read couldn't map back to its source: the inspector couldn't read its source or its blocks, Bun gave it no map, its own map couldn't be read, or Bun's map names more than one source;
  - a loaded script whose map names a source its install doesn't hold;
  - a built script of the changed package whose map couldn't be read, or a built directory that couldn't be listed.
- A source file no profiled host loaded is named with all its changed lines, since none of them ran, whatever they hold. A reason from the bullet above changes that, and so does a build of the file into more than one script. Then the file isn't named: its lines are counted among those the comment couldn't tell about. Lines its package's built maps place as no code are counted apart. A file a profiled host loaded counts as loaded even where nothing in it maps to code, such as a module of types alone.
- A line that maps to nothing the host runs, such as a type or a comment, is counted apart. Two cases differ. In a file named as one no profiled host loaded, it's named with the file's other lines. In a loaded file built into more than one script, or in a loaded file while a host loads a built script with no map, it reads "couldn't tell", since another script may hold its code. For a file no profiled host loaded, which lines map to code comes from the package's built maps, where there are some. There a changed function's closing brace can map to code, where in a loaded file it maps to none.
- A source file can be built into more than one script. Then its lines not seen to run read "couldn't tell", naming the scripts. The script a host loaded may hold only part of the file's code. So a deletion with no code beside it there reads "couldn't tell" too.
- A changed file that isn't script source, such as a binary or a text file, can't be read back to lines a host ran. Its change reads "couldn't tell", naming the file.
- A line maps to code where the package's own map says so. tsc maps every statement it emits to the line it came from. Code it adds itself, such as a helper, maps to no line.
- Only the changed package's own installs are read. A copy of its code inside another package would run unseen, and its lines could read as not run.
- A hunk that only deletes lines is judged by the nearest code line on each side of it on the head: reached when either ran. Where neither side has a code line, as in a file of types alone, there's nothing on the head to judge it by.

## How a run's name reads

A run's name is its setup and its workload, `SETUP/WORKLOAD`, with a variant after a second slash where there is one, as in `H1/W7/merges-refused`.

## The setups

In every setup but `Hoff`, the host has the modules a recipe that names none gets, the wake gate and the workspace among them, less subagents, which `H2`'s and `H5`'s setups and `W9`'s and `W14`'s workloads turn back on; `H5` also turns on lessons and retrieval, which such a recipe doesn't get. Its timers from 30 s up to 2^31−1 ms run on the workload's clock, so they fire only when a step moves that clock to or past them; its monotonic clocks read real time plus every move of the workload's clock, so a deadline it keeps on one passes in real time too, or at a step that moves the clock past it, as `harness/README.md` says. A turn the host holds for a provider's stated wait, and a wake that waits in that hold, end a step as held, since only a later step's move of the clock ends the hold; a budget hold, which waits on compression rather than the clock, ends none; a hold still standing at a checkpoint, a restart or the run's end fails the run, naming it.

## Where runs start

W1, W2, W12, W13, W16, W17 and W19 runs, H2's run, the two no-tools runs, P4's continuation, `H1b/continuation/fresh`, `H1b/W14` and `H4/W15` start empty, and P4's continuation and `H1b/continuation/fresh` build their history first in the run itself. W12, W13, W16, W17, W19, `H1b/W14` and `H4/W15` are too short to compress, so their runs' stores hold no summaries, and checks 4 and 5 have none of their stores to judge. The other continuation runs, and the rest, continue from a conversation the harness builds first, never a captured real session: the continuation from a conversation it builds for that purpose, and the rest from their own setup's W2 store, or W1's for H3, which doesn't summarise. The harness builds these with the fixed host release that `harness/stack.json` names, the same on both sides of a view, so a difference comes from the run, not from where it started. `H1b/continuation/from-0.9.0`, `/from-0.20.0` and `/from-0.23.0` start instead from a prefix the release their name gives wrote, also the same on both sides.

P4's continuation builds that conversation itself, in the same run and with the host under test, since the fixed release can't send OpenRouter requests to the stand-in: its OpenRouter adapter takes no base URL. Its host then stops and boots that conversation again a day later, as a run that continues a conversation the harness built boots it a day after its end. So P4's history is written by the host under test, as `H1b/continuation/fresh`'s is and the other providers' continuations' aren't, and its record holds that history's requests too: a change that moves them shows there.

A run that starts from a stored conversation also starts from the cache receipt its last request left. Under kv-unified folding, the default, the first compile weighs cache costs only while the tools in the agent's tool list and its system prompt are the ones that receipt was written for. So a change to a tool in the agent's tool list, though not to one inside a toolset, or to the system prompt, can change how such a run's first compile folds, as it would a resident's first compile after it takes such a change. A run's token calibration moves when the tools its requests carry change, as a resident's would, and so do the token counts it prices with it, such as the total a summariser is told it's reading; the size of that move here comes from the stand-in's own count of the tools.

## The checks every run is judged by

The checks are numbered 1–6 and 10–15, the numbers each run's report and a view's flags use; there are no checks 7–9. Each counts what it judged. Where a check applies to a run and judged nothing, that's a couldn't-judge flag, never a pass. A view sets each run's flags on the head against the base's: new, gone, or kept.

### Check 1: every turn answers

It flags a request the stand-in couldn't answer, which it names with its reason, or couldn't classify; an inference that failed; an alert the host raised; a step that didn't settle; an answer that reached no channel; and a scripted reply left unused.

The driver waits for each turn's spoken answer to end, and agent-framework ends one in one of four ways, at 0.32.0 and 0.33.0 alike: it publishes it to a channel; it can't route it, and says why; it holds it as drafts, and says why; or it keeps it private, as `skip_reply` asks, or leaves it unrouted where the recipe turns plain speech off, which only the turn's `[delivered]` receipt says. agent-framework's trace of a receipt names no agent, at 0.33.0 and on its `main`, so the driver takes a receipt as the turn's only where no other agent's turn was alive from the speech to the receipt, and otherwise fails the run, saying it can't tell. A turn whose trigger keeps it silent sends its answer nowhere by design, and the driver doesn't wait for it. A step can say its turn ends another way: with no speech, as a refused turn nothing retries does, where the driver waits for its inference to complete and fails the run if the turn spoke after all; or with its speech contained, as agent-framework's tool-wrapper guard contains a reply that is a whole tool wrapper, sending, holding and receipting none of it, where nothing follows the speech to wait for. Speech of whitespace alone, and the private envelope of a turn under explicit routing, end in none of those ways, so the driver's wait for them runs to its bound and the run fails, naming the wait. From connectome-host#555 on, the host says a round that ended without tool calls held no text, where a host before it said nothing; that isn't speech, so a turn whose script ends it with no speech passes, and a turn whose script has it speak waits on for a round that speaks, as agent-framework's retry after a refusal's rewind or an `unstick` does in the same turn, and fails the run at the wait's bound, naming the wait, where none comes.

A turn no addressed message woke, such as one that console input, a timer, a reminder, an ambient or judged batch, the heartbeat or the suppression review's notice wakes, has no channel to answer on unless the recipe gives it one: the host can't route its answer, or holds a heartbeat's or a reminder's as a draft, and tells the resident so in its next request, whose record shows it. ### Check 3: request shape and budgets

Every request the stand-in answers is well formed: roles alternate, each result answers a call in the message before it, and each call before the last message has its result in the message after. On the Messages API a turn's tool results also come before anything else in it, as the tool-use page says: "In the user message containing tool results, the `tool_result` blocks must come FIRST in the content array". A message here is a turn: on the Messages API, the messages one role sends in a row, which the API combines into one turn, as a prefill's transcript and its continuation are; on the Responses API, the items one side sends in a row; on the Chat Completions API, a wire message, with a `tool` message and the message after it joining their side's turn. Each request also fits the bound that governs it: the model's window for a compiled request (a turn's first, or a stream restart's), and agent-framework's stream bound for a later round.

### Check 4: coverage

For setups that compress, every stored input and reply goes out in each request, raw or inside a summary sent, once for each stored row that carries it, and in order: where the host presents the agent's window, the order its rows entered that window, and store order otherwise. agent-framework presents a row that arrives during a turn at the turn's end or a tool boundary, after rows the turn stored after it, so the two orders differ there. A row the window doesn't hold when the run ends has no place in its order, and isn't judged for it; the run's report counts such rows, each once whether it went out raw or under a summary, beside what check 4 judged, and counts apart a canary that no row the final store holds carries. A row another stores that quotes a message carries its canary too, as connectome-host's knowledge retrieval stores one after a message, opening "## Retrieved Knowledge, for the message beginning" and the message's text, so the message's canary goes out once in each, and a request that carries it more often than the rows that carry it is flagged. An event's place in the window's order is its own row's, the first that carries its canary. A gate line quotes the events its batch held where agent-framework delivers the batch, after rows stored since, as W12's console input, stored at arrival, is quoted by its batch's line at `mix.fire`, so an event the request carried before the line, raw or under a summary, isn't judged for order again where the line quotes it; anything else in the line's block, such as a row the Chat Completions API joins before or after it, is. The line is told wherever it opens a line of its block, so a gate line the Chat Completions API joins after an earlier row of its message is told too. From agent-framework v0.29.0 the text a participant or a server supplies is stored with each `[Gate` marked, so none of it reads as the line. Text agent-framework never marks would: the agent's own words and summaries on any API, and tool results where they're text, on the Chat Completions API and membrane's XML formatter. So would a row a release before v0.29.0 stored: of the views' starting conversations only `from-0.9.0`'s is that old. No run puts gate text in any of these, and a workload that did, such as a log or a transcript in a tool's output, would need the line told by more than its place. Check 4 can't tell which of those rows a canary that went out came from, so a request that carries it at all isn't flagged for leaving one of them out; check 11 judges each row the window holds, and none it reads out of the window. A row a suppress rule hid, which agent-framework stamps `metadata.suppressed` and never renders, is owed to no request; its suppression review is a row of its own, which may quote it, and is owed as any row is. What the script says a step's rewind sheds (a step's `sheds`: W16's refused round, the sixth turn's message and, at the unstick, the breaker retry's reply) is owed to no request from that step on, the one it was shed from included, which W16 judges carried it, also where the host presents the agent's window, whose rewind takes the rows out of the window and leaves them stored (agent-framework 0.33.0, `shedNewestTurn`). A summary the split-stitch rung stitched from several summariser answers carries each answer's mark, and each maps to it where it goes out in the same block as the summary's first mark. A summary a later removal drops isn't in the final store, so check 4 can't map it in a request sent before the drop, and flags it there; no run drops a summary today.

A message the script delivers on a channel its tune-out holds (a step's `tunedOut`) is owed to no request of the resident's, since agent-framework holds it from the resident's view. The rule holds it to the run's end, also where its hold ends, as `H4/W1`'s scope of every channel but one does: agent-framework 0.33.0 keeps a held row from residents by its stamp (`residentViewFilter`), whether or not its hold still stands, and gives the resident a released backlog as a notice of its own that quotes it. Where agent-framework sent a held row itself to the resident, check 11 would flag it. Under reader forks (`H4b`), each fork is shown in its framing what was held since the last look, and its view filter keeps the held rows themselves out of its compiles (agent-framework 0.33.0, `invokeReaderFork`). So each held message must reach the fork's requests at the step that delivered it, and one that no fork request at its step carries is flagged. A reply an operator's `/undo` took out of the resident's window is owed to no request after it, where the script says so: W1's `/undo` takes out the resident's last turn, under reader forks the third wake turn's note, and under the persistent reader, which wakes no turn of the resident's, the turn that tuned `chat` out. One sent raw after it anyway is flagged.

### Check 5: bookkeeping

Every summary declares as its sources only what its summariser request showed: the messages it covers, or the summaries it merges. A stitched summary is judged against what all its parts' requests showed, and a message it left out as a placeholder passes where its text names that message, since context-manager declares it on purpose. A store with no summaries, under a setup that compresses, is flagged.

### Check 6: windows raw

Each request carries raw the two turns before its own, less what an operator suppressed, rolled back or undid, what a rewind shed, as the script says, and what the script's tune-out holds, as for check 4, and each stretch's last request carries the head and the raw tail the host reported, less what a rewind shed or an `/undo` took out, which a store whose window is presented keeps.

### Check 10: calibration edge

For adaptive setups, a calibration multiplier at the clamp's edge (0.6 or 1.8) makes the run invalid, since its folds are clamped.

### Check 11: compile invariants

What the harness found wrong with each compile context-manager made, judged against the store it compiled from:
- everything stored goes out, raw or under a summary, and in order, the window's order where the host presents the agent's window, as for check 4, but a turn an `/undo` or agent-framework's shed took out of the agent's window, a row out of the window without an undo, as one that arrived during a turn is until the turn's end or a tool boundary presents it, which a compile inside the agent's call (a fork's, or a dry one) meets, or one taken out without an undo, each named by the status context-manager's `windowStatusOf` reads at the compile, a message a suppress rule hid, which goes out in neither form, a reasoning-loss notice agent-framework 0.28.0 to 0.31.x stored, marked `system` and `reasoning-loss`, which from agent-framework #974 on goes out in neither form, and, to the resident and its reader forks, a message the script delivered on a channel it had tuned out, named by the canary its own text opens with, which goes out to a persistent reader or in a fork's framing alone, whatever the host stamped on it;
- nothing goes out raw beside its own summary;
- the compile keeps to its budget, or refuses;
- a call and its result aren't sent apart;
- a message's thinking goes out with its calls, or not at all;
- a summary over pinned messages is at a level the pin allows.

A reasoning-loss notice quotes the start of a reply it names, that reply's canary included, so where an agent-framework from before #974 sends one, check 11 flags the notice as sent anyway, and check 4 flags the quoted canary, raw or under a summary that begins at the notice, as carried out of its window's order, after rows stored after the reply it quotes: in `H1b/continuation/from-0.20.0`, 8 flags of each. From #974 on neither check flags, since no request carries the notice. agent-framework 0.34.0 is the first release with #974, so every view whose arms install an earlier one shows these 16 flags on both arms of that run, equal on both sides, and the comment lists none of them as differing. Today that is every view on connectome-host `3e715b4`, whose lockfile installs agent-framework 0.33.0, unless the view lays a newer one over. They end when the host's lockfile reaches 0.34.0.

Because the notice carries the quoted reply's canary, the checks that tell rows by their canaries can take one for the other. Check 4 owes that canary once for each row that carries it, so beside an unsent notice a second copy of the reply passes, and where the notice is sent a dropped reply passes. Check 5 takes the reply's showing in a summariser request for the notice's. Check 6 slices a head or tail from every stored row, the notice included, though agent-framework from #974 on leaves the notice out of the window, so a tail that reached back to it would be read one row off. Check 11 tells rows by id, so it flags the notice sent, raw or under a summary, and the reply dropped, and no run's tail reaches back to the notice. The run's product takes any notice in its final store for the prefix's, which holds only because no agent-framework from 0.32.0 on writes one. If a later one wrote reasoning-loss notices again, the product would need the prefix's notice by identity.

Check 11 judges that a compile sends its window. Whether the window has presented a row by a given request is judged elsewhere: by check 6, for the scripted inputs and replies of the two turns before each request; by check 4, for every stored input and reply before a request's input, in a setup that compresses; and by W14's and W17's arrival rules, for where a row that arrived during a turn first goes out. No check judges a row with no scripted canary, such as a receipt or a notice, or one whose canary another row carries too, such as a retrieval row, that a window wrongly reads out of the window, nor what any dry compile leaves out. A pull request that caused either would still show in the view's difference between its arms; one already in both arms goes unflagged.

### Check 12: reloads

At a restart with a reload check, the compile after the boot matches the one before the shutdown: the same outcome, the same messages from the same stored sources, and the same system injections.

### Check 13: pairing

Every compile made for a request reached it: the agent's next request to arrive at the stand-in. It judges each agent that compiles, subagents and readers included. The stand-in tells a subagent's requests from the run's agent's by a marker the script puts in the subagent's system prompt, or in a reader fork's voice block, and one subagent's from another's where the workload labels each by the name it spawns it with: the record and the checks read that name from the subagent's agent name, which connectome-host writes `spawn-<name>-<stamp>` (`subagent-module.ts` `nameStamp`). The other agents, such as reader forks or subagents the workload doesn't label, are told apart by step: a request of theirs belongs to the one of them that compiled in its step. Where two of them compile in one step, or such a request comes in a step where none compiled, none of them is judged and the run's record isn't written. A labelled subagent whose agent name isn't in that form has no compiles the record can match to its label, and the run's record isn't written; so too where two agents' names read as one label, or where labels are in use and an unlabelled agent compiles while no request is recorded on the unlabelled side. Where a compile went out in no request, the run's report gives under its flag every failure, giving up, wait to retry, and stop or turn dropped before it sent, with its reason, that the host reported in that step, every agent's, whole, so what kept the request from going out can be read there.

### Check 14: the workload's own property

Each workload's property, as described above. A workload whose property is another check's, as the continuation's is check 2's, most W7 variants' check 1's, and W9's check 12's, is held to that check's count.

### Check 15: binding control

On a model that binds thinking and takes the drop control, every agent request to such a model carries the host's rule for a changed thinking block, `prefix_mismatch_behavior: drop_block`, and asks for the beta that control needs.
