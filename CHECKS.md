# What a context view runs and checks

A context view runs the whole connectome-host, with its real agent-framework, context-manager, membrane and chronicle, through 66 scripted runs. It does this twice: once on the pull request's base, and once with its head merged onto the base. A stand-in answers for the model's API, Anthropic's, OpenAI's Responses API in P1's run, ChatGPT's Codex backend in P2's, Amazon Bedrock's in P3's, or the Chat Completions API as OpenAI documents it in P5's and as OpenRouter serves it in P4's, so no model is called and every answer is the same each time. Each run records every request the host sends, and is judged by the checks below. The comment then says which runs' records changed between the two, and which flags one side raised more times than the other.

The harness that does this is in `harness/`. Its `README.md` gives each check's exact rules, in "What each run's checks judge".

## What a view's comment rests on

The pull request's own code runs in the job that makes these records, so everything a view reports from its runs rests on that code acting in good faith. A view isn't a security check.

A view speaks only for its runs: a case of the change that none of them reaches doesn't show in its records.

Each run has one resident, since connectome-host runs one (`agents: [agentConfig]`), so a change to what residents sharing one slot are shown doesn't show in any run.

Some settings of the kv-unified solver reach nothing on the continuation at context-manager 0.25.0, so a change to what they govern doesn't show there: pinning the subtree engine, since an unpinned engine is the subtree engine until the label ceiling, which no continuation run reaches; turning the hysteresis certificate off, which by its doc can change a bucketed solve's choice but moved nothing in a run with it off; treeifying summaries over gaps and preserving them (`treeifyNonContiguousSummaries`, `preserveGapBearingSummaries`), which act only on a store that holds a summary over a gap, and none of these stores does; and measuring producible merges one at a time (`latentDemandMode: 'individual'`), which moves nothing on the continuation, by a run of C11h's settings one at a time. C11h sets the last two, and no setup sets the first three.

A record holds what each request carried, as its text and hashes, not how many tokens it held or what it would cost, so a view, which compares records, can't show what a change costs.

On a model that thinks only when asked, such as Claude Opus 4.6, H1's and H3's model, the stand-in answers a script's thinking whether or not the request asks for thinking, where the provider sends none unasked. So a change that stops or starts asking for thinking on such a model doesn't show in what the stand-in sends back.

In P1's and P2's runs, on OpenAI's Responses API and ChatGPT's Codex backend, a record holds each item a request sent by its own digest. A reasoning item's content and a compaction item's are opaque, so a change to them shows as an item's digest moving, with no text to read. The values membrane draws at random on the Codex backend, its cache key and `session_id` header, are written by their shape and numbered by first appearance in the run, so they make neither two arms nor a run's self-check differ, while a change in which requests share a key does. In P5's runs, on the Chat Completions API, a record holds each message a request sent by its own digest, the system prompt among them, and an image in a tool result goes as membrane's text in its place, so a change to the image itself shows nowhere. P3's runs, on Amazon Bedrock, are recorded as the Messages API's, with the Bedrock model and route in each head. `harness/README.md`'s "Reading a record" says how each line reads.

Where records differ, a model reads the differences and writes the account at the top of the comment. Code checks that the account covers every difference between the records of the runs that could be compared, and that its quotes are copied from the records. It also checks that the account's prose has no numbers of two or more digits, decimals or hashes, no counts of runs, steps, compiles, requests or rounds, and none of the records' notation. The comment gives its own counts of runs, changes and steps. Nothing checks whether its sentences are true.

## How a run's name reads

A run's name is its setup and its workload, `SETUP/WORKLOAD`, with a variant after a second slash where there is one, as in `H1/W7/merges-refused`.

## The setups

In every setup the host has the modules a recipe that names none gets, the wake gate and the workspace among them, less subagents, which `H2`'s and `H5`'s setups and `W9`'s and `W14`'s workloads turn back on; `H5` also turns on lessons and retrieval, which such a recipe doesn't get. Its timers from 30 s up to 2^31−1 ms run on the workload's clock, so they fire only when a step moves that clock to or past them; its monotonic clocks read real time plus every move of the workload's clock, so a deadline it keeps on one passes in real time too, or at a step that moves the clock past it, as `harness/README.md` says.

## Where runs start

W1, W2, W12, W13, W16 and W17 runs, H2's run, the two no-tools runs, P4's continuation, `H1b/W14` and `H4/W15` start empty. W12, W13, W16, W17, `H1b/W14` and `H4/W15` are too short to compress, so their runs' stores hold no summaries, and checks 4 and 5 have none of their stores to judge. The other continuation runs, and the rest, continue from a conversation the harness builds first, never a captured real session: the continuation from a conversation it builds for that purpose, and the rest from their own setup's W2 store, or W1's for H3, which doesn't summarise. The harness builds these with the fixed host release that `harness/stack.json` names, the same on both sides of a view, so a difference comes from the run, not from where it started.

P4's continuation builds that conversation itself, in the same run and with the host under test, since the fixed release can't send OpenRouter requests to the stand-in: its OpenRouter adapter takes no base URL. Its host then stops and boots that conversation again a day later, as a run that continues a conversation the harness built boots it a day after its end. So P4's history is written by the host under test, unlike the other four providers', and its record holds that history's requests too: a change that moves them shows there.

A run that starts from a stored conversation also starts from the cache receipt its last request left. Under kv-unified folding, the default, the first compile weighs cache costs only while the tools in the agent's tool list and its system prompt are the ones that receipt was written for. So a change to a tool in the agent's tool list, though not to one inside a toolset, or to the system prompt, can change how such a run's first compile folds, as it would a resident's first compile after it takes such a change. A run's token calibration moves when the tools its requests carry change, as a resident's would, and so do the token counts it prices with it, such as the total a summariser is told it's reading; the size of that move here comes from the stand-in's own count of the tools.

## The workloads, and what each checks

Each workload is a scripted conversation with a property of its own, which is check 14.

### `continuation`

Five short stretches: summaries closing and merging; a tool round with an image; three calls at once; a call after thinking; and a long tool turn of four rounds, answered badly (with thinking only, empty, and cut at `max_tokens`). It checks that each stretch produces what it exists to produce, such as a merge or a request carrying both results with one an image (check 2). A setup that doesn't summarise declares nothing for the first stretch or the last, one without adaptive resolution declares no message stored in parts, since only adaptive resolution stores a long message so, and one whose merge threshold is 0 declares no merge. Under H6 a tool round's products are read in the prefill's transcript: each result by its call's canary inside `<function_results>`, the round's image as a user message of its own right after its call's result, its placeholder inside that call's own result, and a call led by thinking that opens the agent's turn in literal `<thinking>` tags.

### `W1`

70 ordinary turns, some with tool calls. It checks that the store's summaries reach level 3 by the end, for setups that summarise. Under H4, the agent then tunes its channel out and the reader reads six messages for it, with an `/undo` before the fourth.

### `W2`

70 turns heavy with reading-sized tool results, with an image attached every seventh turn and a long document pasted every tenth. It checks that the store's summaries still reach level 3 by the end.

### `W4`

Four turns that each think before a tool call. It checks that none of those calls goes out without the thinking that led to it, ahead of it in its message.

### `W5`

The tool-result guard is turned on, then twelve turns with tool results, every other one large and mixing text and an image, too large for one stored message. It checks that the store keeps both the call and the result of each, and that a message stored in parts never goes out whole without its tool blocks.

### `W6`

Twelve turns of awkward tool pairing: two calls at once, a call id reused across two rounds, a call the tool server never answers, which times out, and a suppressed message. It checks that no request carries membrane's repair mark for an unpaired call or result, which would mean context-manager handed one over unpaired, and that the held call did time out.

### `W7`

Summariser failures, over 21 turns, or 32 with no tools. Under H2, the knowledge subagent does the tool work in one long task. Its variants:

- **`merges-refused`:** the stand-in answers every merge with a refusal, as a model declining would. It checks that each refusal raises exactly one alert, and nothing else raises one.
- **`merges-rejected`:** the API rejects every merge with an error instead of a refusal. It checks that every turn still answers and the errors raise no alert (check 1).
- **`chunk-refused`:** the stand-in answers with a refusal every summariser request that carries one turn's marked content. It checks that the content reaches the summariser only in the slice it's asked to remember, never in a merge, and that each refusal raises one alert.
- **`no-tools`:** an agent with no tools, starting empty. Nothing is refused, and it checks that every turn answers and nothing raises an alert (check 1).
- **`fable-no-tools`:** the same, with a Fable-family model set to write the summaries. Where that model writes none, both sides carry a no-summaries flag.

### `W8`

Sixteen turns. Before turn 5 an operator cuts the budget to 60%, before turn 9 to the edge (the response reserve plus 1,000 tokens), and before turn 13 restores it. It checks that a setup that compiled every turn before the cut does so again within two steps of the restore. Under H4, the cuts apply to the reader while it reads tuned-out messages. Its variants:

- **`enforced`:** with budget enforcement on.
- **`unenforced`:** with budget enforcement off.

### `W9`

Twenty turns of lifecycle events: a close and reopen; pins listed, added and removed; the raw tail's size set; a restart that marks earlier turns as a record the agent inherited, with its own wording for the instruction to remember such a record and for the reminder after it; a forked subagent; a changed system prompt; `/undo` and `/redo`; `/newtopic`; the tool-result guard turned on; a suppressed message; a changed head window; and a rollback of the record to an earlier message with `/branchto`, before the last turn. It checks that the store, closed and reopened at turn 3, compiles what it compiled before closing (check 12). The other events are there for every check to judge across.

### `W11`

Fourteen turns. By turn 8 an operator has pinned older messages at several levels, pinned a tool result and marked a document. Before turn 9 the budget is cut to 35%, and before turn 13 it's restored. It checks that each pin, when added, lists exactly one new pin and none gone, and that every pin and mark placed by turn 8 is still there, unchanged, after turns 12 and 14. A compile that can't hold them must refuse instead. Under H1, the second turn first meets one overloaded error, which agent-framework retries.

### `W12`

The wake gate's paths, from empty, with the recipe's starting rules naming one channel each. The agent opens the host's built-in `settings` toolset and looks at each tool its listing names, so its own requests carry those tools' whole definitions, which the agent's tool list never does. Then: a message the `always` rule wakes it for; one the `defer` rule holds back; two messages in one `debounce` window, delivered as one batch at the step that moves the clock past it; the same window's message the agent has already read and answered in a turn another channel woke, before the window ends; a `rate_limit` bucket of one, whose second message is denied; a `passive_sample` of every second message, with `passthrough` and a `defer` rule after it; a `judge` rule's two batches of two messages each, the first carrying `[[wake]]`, which the stand-in's reply judge answers REPLY for, so the batch wakes the agent as a debounce's does, and the second without it, which the judge lets go by; where the host's agent-framework brings suppression, a `defer` rule with `suppress` over a muted channel and two messages there, the second carrying `[[flag]]`; where it brings wake onboarding, a `defer` rule that matches a message's text, `[[quiet]]`, and so names no server, channel or tag, letting by undecided a message addressed to the agent, so the fixture server's first such message brings the onboarding notice of what its tag ontology suggests and wakes the agent, which accepts it, after which a message carrying the suggested tag wakes the agent by the rule accepting wrote, and the second server's first such message brings the notice of the one rule the host offers a server that suggests nothing, which the agent declines, after which its next such message wakes nothing; the agent's `sleep`, through which a message on the `always` channel doesn't wake it and a privileged user's does, and a second `sleep` whose end wakes it; `skip_reply` with `wake_in_seconds`, which wakes it; a rule the agent adds through the toolset, which holds its channel's next message back, and removes, after which that channel's next message wakes it, beside a `gate_status` call; `set_channel_mode` setting another channel to debounced, so two ambient messages there come as one batch; ## The checks every run is judged by

The checks are numbered 1–6 and 10–15, the numbers each run's report and a view's flags use; there are no checks 7–9. Each counts what it judged. Where a check applies to a run and judged nothing, that's a couldn't-judge flag, never a pass. A view sets each run's flags on the head against the base's: new, gone, or kept.

### Check 1: every turn answers

It flags a request the stand-in couldn't answer, which it names with its reason, or couldn't classify; an inference that failed; an alert the host raised; a step that didn't settle; an answer that reached no channel; and a scripted reply left unused.

The driver waits for each turn's spoken answer to end, and agent-framework ends one in one of four ways, at 0.32.0 and 0.33.0 alike: it publishes it to a channel; it can't route it, and says why; it holds it as drafts, and says why; or it keeps it private, as `skip_reply` asks, or leaves it unrouted where the recipe turns plain speech off, which only the turn's `[delivered]` receipt says. A turn whose trigger keeps it silent sends its answer nowhere by design, and the driver doesn't wait for it. A step can say its turn ends another way: with no speech, as a refused turn nothing retries does, where the driver waits for its inference to complete and fails the run if the turn spoke after all; or with its speech contained, as agent-framework's tool-wrapper guard contains a reply that is a whole tool wrapper, sending, holding and receipting none of it, where nothing follows the speech to wait for. Speech of whitespace alone, and the private envelope of a turn under explicit routing, end in none of those ways, so the driver's wait for them runs to its bound and the run fails, naming the wait.

Of those, check 1 flags: an answer the host couldn't route, whenever a message the script addressed to the resident woke the turn, since that turn had a channel to answer on, and whenever the host's reason is anything but that the turn had no locus; an answer held as drafts because an explicit send in its turn or a routing prefix held it back, on any turn but one whose step says it's held for that reason, as W13's routed turn under explicit routing does, since no other step's script has its speech held so, so a hold for either reason held what the host should have sent; an answer held as drafts for having no destination, whenever an addressed message woke the turn, unless its step says it's held so, as W13's are under a lock to drafts; and a receipt saying a turn's speech could be neither sent nor held as drafts, so the host lost it, which check 1 reads from the receipt's own words, as agent-framework 0.32.0 and 0.33.0 write them, in each request in which an agent's count of such receipts rises above its count in that agent's previous request. A turn no addressed message woke, such as one that console input, a timer, a reminder, an ambient or judged batch, the heartbeat or the suppression review's notice wakes, has no channel to answer on unless the recipe gives it one: the host can't route its answer, or holds a heartbeat's or a reminder's as a draft, and tells the resident so in its next request, whose record shows it. That isn't flagged. The script says which of its steps no addressed message wakes, so the check doesn't depend on how a host decides where a turn speaks. Two things are left to a workload's own check: the turns W8 and W11 allow to fail under a budget cut, and the refusal alerts that W7's `merges-refused` and `chunk-refused` count for themselves. And one such receipt can go unflagged: agent-framework's words for the lost speech give only how many segments it lost and the draft store's error, at 0.32.0 and 0.33.0 alike, and the rest of the receipt, the turn's other notes and where its speech went, needn't differ from another's, so check 1 can't tell two such receipts apart and counts them; a new one that arrives in the request where an older one leaves the window keeps the count where it was.

### Check 2: declared products

Each continuation stretch produced what it declares: a summary, a merge, a request carrying both results with one an image, a call led by its thinking, and the like.

### Check 3: request shape and budgets

Every request the stand-in answers is well formed: roles alternate, each result answers a call in the message before it, and each call before the last message has its result in the message after. On the Messages API a turn's tool results also come before anything else in it, as the tool-use page says: "In the user message containing tool results, the `tool_result` blocks must come FIRST in the content array". A message here is a turn: on the Messages API, the messages one role sends in a row, which the API combines into one turn, as a prefill's transcript and its continuation are; on the Responses API, the items one side sends in a row; on the Chat Completions API, a wire message, with a `tool` message and the message after it joining their side's turn. Each request also fits the bound that governs it: the model's window for a compiled request (a turn's first, or a stream restart's), and agent-framework's stream bound for a later round.

### Check 4: coverage

For setups that compress, every stored input and reply goes out in each request, raw or inside a summary sent, once, and in order: where the host presents the agent's window, the order its rows entered that window, and store order otherwise. agent-framework presents a row that arrives during a turn at the turn's end or a tool boundary, after rows the turn stored after it, so the two orders differ there. A row the window doesn't hold when the run ends has no place in its order, and isn't judged for it; the run's report counts such rows, each once whether it went out raw or under a summary, beside what check 4 judged, and counts apart a canary that no row the final store holds carries. A summary the split-stitch rung stitched from several summariser answers carries each answer's mark, and each maps to it where it goes out in the same block as the summary's first mark. A summary a later removal drops isn't in the final store, so check 4 can't map it in a request sent before the drop, and flags it there; no run drops a summary today.

### Check 5: bookkeeping

Every summary declares as its sources only what its summariser request showed: the messages it covers, or the summaries it merges. A stitched summary is judged against what all its parts' requests showed, and a message it left out as a placeholder passes where its text names that message, since context-manager declares it on purpose. A store with no summaries, under a setup that compresses, is flagged.

### Check 6: windows raw

Each request carries raw the two turns before its own, less what an operator suppressed or rolled back, and each stretch's last request carries the head and the raw tail the host reported.

### Check 10: calibration edge

For adaptive setups, a calibration multiplier at the clamp's edge (0.6 or 1.8) makes the run invalid, since its folds are clamped.

### Check 11: compile invariants

What the harness found wrong with each compile context-manager made, judged against the store it compiled from:
- everything stored goes out, raw or under a summary, and in order, the window's order where the host presents the agent's window, as for check 4, but a turn an `/undo` or agent-framework's shed took out of the agent's window, a message a suppress rule hid, which goes out in neither form, and, to the resident, a message the script delivered on a channel it had tuned out, which goes out to its reader alone, whatever the host stamped on it;
- nothing goes out raw beside its own summary;
- the compile keeps to its budget, or refuses;
- a call and its result aren't sent apart;
- a message's thinking goes out with its calls, or not at all;
- a summary over pinned messages is at a level the pin allows.

### Check 12: reloads

At a restart with a reload check, the compile after the boot matches the one before the shutdown: the same outcome, the same messages from the same stored sources, and the same system injections.

### Check 13: pairing

Every compile made for a request reached it: the agent's next request to arrive at the stand-in. It judges each agent that compiles, subagents and readers included.

### Check 14: the workload's own property

Each workload's property, as described above. A workload whose property is another check's, as the continuation's is check 2's, most W7 variants' check 1's, and W9's check 12's, is held to that check's count.

### Check 15: binding control

On a model that binds thinking and takes the drop control, every agent request to such a model carries the host's rule for a changed thinking block, `prefix_mismatch_behavior: drop_block`, and asks for the beta that control needs.
