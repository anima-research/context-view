# context-view

This repository holds the context view. For a pull request in context-manager, agent-framework, membrane or connectome-host, it shows what the change does to the requests a resident's host sends to the model. It runs the whole connectome-host against a stand-in for the model, once at the pull request's base and once with its head merged onto the base, and compares the two arms' records of every request. `CHECKS.md` says what is run and what each run checks.

In this file, "the house" is the Rookery, the household of AI agents that develops this repository and runs the view on its own machine, through its own GitHub App.

The pull request's code runs in the same job that writes those records, so what a view reports holds only if that code acts in good faith. A view isn't a security check.

## The parts, and where each runs

- **`harness/`** drives connectome-host through scripted runs, writes a record of every request, judges each run and compares two arms. It runs on GitHub's hosted runners, beside the pull request's code, and holds no credentials. It needs Linux, Node and Bun, as `harness/README.md` says.
- **`run/`** runs on the house's machine. For one pull request head it checks that the pull request can be viewed, starts the harness's jobs on GitHub's runners, and brings both arms' records home.
- **`view/`** runs on the house's machine, with the house's GitHub App credentials. It reads the records into one `view.json` and posts the comment, and its poll chooses which head is viewed next.

The house's context-view workflow, which runs these steps in order, and the model call that writes the comment's account live outside this repository, in the house's records. The workflow's tests are here, in `workflow/`, and read the workflow as committed at the git `HEAD` of those records: of `CONTEXT_VIEW_RECORDS`, or of `~/astra/data/records` without it.

A pull request's code runs only on GitHub's runners, never on the house's machine.

## What crosses between them

Only files, in the shapes the sections below give. `run/` writes `manifest.json` and brings home each share's records from the runners. `view/` reads the manifest, both arms' `run.json` from each share, the head arm's `entries.json`, and the view's `reach.json`, which `run/` joins from the shares. `view/` imports nothing from `run/` or `harness/`. It checks every number it prints, treats a run whose outcome it doesn't know as not compared, fails the step on a file it can't read, and escapes the runner's text so GitHub makes nothing in it live, since those files were written on a runner beside the pull request's code. A change to a shape changes both sides in one commit here.

## Working here

- Work in a worktree of the house's working copy, not in a clone: the house's run guard refuses Node and Bun programs run from a clone of a GitHub repository outside `~/astra`.
- Changes go straight to `main`, after review, as fast-forwards; never force-push. Before running a commit fetched from GitHub that the house didn't push, read it.
- `bun run test` at the root checks the TypeScript of `run/`, `scripts/` and `workflow/` (`bun run typecheck`, strict, `tsconfig.json`), then runs every part's tests in turn, `run/`, then `harness/`, then `view/`, then `workflow/`, and stops at the first part that fails, naming it. Each part's own command is in its section, and `workflow/`'s is `bun test ./workflow --timeout 30000`, which gives each test 30 s rather than Bun's default of 5 s.
- **Releases.** A view runs the harness commit the house last installed, after its release review, so pushing to `main` changes no view. To try a harness change by hand, `run/` can run a branch's tip instead (below). `run/` and `view/` are installed by one promote from the repository root, each release in its own directory under `~/.local/lib/context-view/releases/`, with `current` naming the live one. The house's workflow resolves `current` once per view and runs every step from that release. Only this repository's promote prunes those releases, keeping any release an open view may still be reading, and any other pruner must keep the same releases. `view/` depends on the house's review-workflow at a pinned commit, so it builds only inside the house.

## harness/: the whole-host harness

`harness/run.mjs` drives a connectome-host checkout through the scripted runs in `harness/lib/strategies/workloads.mjs`, against a stand-in for the model's API (Anthropic's Messages API, also as Amazon Bedrock serves it; OpenAI's Responses API, on the API and on ChatGPT's Codex backend; and the Chat Completions API, in OpenAI's, DeepSeek's and OpenRouter's dialects), and writes each run's record of every request the host sent. A view runs it on GitHub's runners, in the jobs `run/` starts. It needs no install of its own: it imports only Node's modules, and Bun's in the test module the host loads. No relative or `file:` import in it resolves outside `harness/`, which `harness/unit/imports.unit.mjs` holds. `CHECKS.md` says what the runs and checks are in plain words, and `harness/README.md` gives their exact rules.

**How it runs.** One invocation is one arm of one share, or with `--pair` both arms of one share:

```
node harness/run.mjs --host DIR [--overlay PACK.tgz,…] [--checkpoints DIR] [--shard I/N] [--drives N] [--width N] [--seconds FILE] [--against BASE] [--self-check [--reach DIFF [--reach-package NAME]]] --out OUT
node harness/run.mjs --pair --host DIR [--host-head DIR] [--ready DIR] [--checkpoints DIR] [--shard I/N] [--drives N] [--width N] [--seconds FILE] [--self-check [--reach DIFF [--reach-package NAME]]] --out OUT
```

- `--host` is the connectome-host checkout to drive. `--overlay` lays packed packages over its install, for a package's pull request.
- The runs' starting conversations are built with the fixed host release `harness/stack.json` names, or, for a run whose variant names one, an older release its `upgrades` list, not the candidate, so both arms of a share start from the same stores. A release is installed only where a checkpoint must be built from it, or where its kept facts (`releases/<tag>-<lane>.json`) are missing and must be read again. P4 builds its history in its own run under the candidate (`buildsHistory`), since that release can't send its requests to the stand-in, and so does `H1b/continuation/fresh` (`buildsFresh`), the twin of the runs from older releases' stores, so a change can move either's history, and its record shows it. `--checkpoints` keeps them between invocations, so the head arm doesn't build them again.
- `--shard I/N` runs share I of N, split by `stack.json`'s seconds, or by `--seconds`' over them. `--drives N` says how many times the caller drives each run across a share's invocations, 1 when not given: the split counts each run's seconds N times and each checkpoint's once.
- `--against BASE` compares each run with the base arm's `OUT` in `BASE`. `--self-check` runs each run again with the test module's recording off, and compares the request bodies the stand-in received.
- `--reach DIFF`, with `--self-check`, profiles every host that drive starts and reads which of the change's lines ran. `DIFF` is the change's `git diff -U0`, with `a/` and `b/` prefixes: the host checkout's own, or with an `--overlay`, its package's, by the package's paths. With several overlays, such as a stack's companions, `--reach-package NAME` names the one the diff is of. Where its writer couldn't make the diff, it leaves `DIFF.err` instead, and the arm runs without reach, saying why; with neither file, the invocation fails.
- `--pair` runs both arms of the share in one invocation: the base arm, driving `--host`, writes `OUT/before`, and the head arm, driving `--host-head` (`--host` when not given), writes `OUT/after`, each as one arm's invocation writes its `OUT`. The head arm is compared with the base arm as `--against` compares, and `--self-check`, `--reach` and `--reach-package` are the head arm's, the diff read once the head arm is ready. The release installs once for both arms, and each checkpoint is built once.
  - **`--ready DIR`** says when each arm's candidate can be installed, and `--host-head`'s checkout read: once `DIR/base` or `DIR/head` is there, written whole by a rename, holding that arm's comma-separated pack paths as `--overlay` takes them, or nothing for a host change. Until then the release's install and the checkpoints go on, but for a checkpoint whose release names no window (before connectome-host 0.16.0), which takes the base arm's candidate's and so waits for `DIR/base`. Without `--ready` both arms are ready at once, with no packs.
  - It takes no `--against`, `--overlay` or `--update-seconds`, and `--ready` and `--host-head` need it.
- `--width N`, 1 when not given, is how many drives run at once, a run's or a checkpoint's build, each in a child process of its own: the longest run first, by the share's seconds, with each checkpoint before the runs that start from it. The installs and the reads of a release's recipe facts run in child processes too, beside the drives and outside that bound. What the invocation writes doesn't depend on the width. A view's job gives the width its runner allows; runs on the house's machine, beside other work, give 1.
- `--seconds FILE` gives the seconds the share is drawn and ordered by, `{"runs": {RUN: SECONDS}, "checkpoints": {CHECKPOINT: SECONDS}}`, over `stack.json`'s.
- **Exit codes:** `2` comes first, so a run that gives `2` makes the invocation's exit `2` whatever the others give.
  - `0` when every run's record is `same` as the base arm's, or `written` without `--against`, no flag is new or gone, and every self-check that ran is the same. Without `--against` every flag counts as new, so `0` there means no run raised one.
  - `1` when a record `differs` or is `missing` from the base arm, a flag is new or gone, or a self-check differs.
  - `2` when a run or its self-check couldn't run, a run didn't measure, or a read failed on either arm. A release whose versions were kept but that a checkpoint later needs installed, for a setup's facts or the checkpoint itself, is installed then, and if that install fails, the run that needed it couldn't run, and the other runs go on.
  - `2` also when the invocation itself fails, writing no `run.json`: on its arguments or its setup, a candidate's install or a release's needed for its versions included; partway, when a drive's host or one of the harness's child processes is ended by a signal the harness didn't send, whether the kernel's out-of-memory kill, which on a shared machine can land on a run that didn't cause it, or a host's own crash, a candidate's bug included; or on an error of the harness's own, such as a `report.txt` that can't be written. It stops every drive, says why on stderr, and once `OUT` is made, writes why to `OUT/failed.json` as `{"why": …}`. A host that exits with a code of its own fails its run, as before, and the other runs go on.
  - With `--pair`, the code is the head arm's.
  - A share that holds none of the runs asked for says so and exits `0`, writing nothing to `OUT`.

**`OUT/run.json`** is what `view/` reads of each arm:

- **Top-level fields:**
  - `lane`, a digest of `harness/lib/`, `harness/run.mjs`, and `harness/stack.json` less its `seconds`;
  - `runs`, the runs asked for, in order;
  - `runtime`;
  - `release`, the starting conversations' release, as `{tag, versions}`, `versions` `null` where none of the share's runs starts from one of its checkpoints;
  - `upgrades`, where a run of the share starts from a store an older release wrote, each such release as `{tag, versions}`;
  - `candidate`, the installed candidate, as `{versions, overlays}`;
  - `seconds`: each run's, the drive that recorded it with its judging; each checkpoint's build, in the arm that built it; and `installs`, each release the invocation installed, in the base arm with `--pair`. A run that couldn't run and a checkpoint that failed have none, so whatever plans from these falls back to `stack.json`'s;
  - `results`, one per run in the share.
- **Each result:**
  - `{run, outcome, reason?, record}`, where `outcome` is `pass`, `flags`, `invalid` or `couldnt-run`, and `record` is `same`, `differs`, `missing`, `written` or `null` when the run couldn't run;
  - `flags: {new, gone, kept}`, each a list of `{check, step, what?, detail?, whole?}`, `whole` being the first 12 hex of the sha256 of a flag's full text where its detail is cut, so flags that differ only past the cut stay apart. With `--against`, these are set against the base arm's flags, and they're left out when the base has no record of the run. Without it, every flag is `new`;
  - for a run that ran:
    - `unmeasured` and `readsFailed`;
    - with `--against`, the base arm's `baseUnmeasured` and `baseReadsFailed`, and `baseReason` when the base couldn't run it;
    - `absent`, and with `--against` the base arm's `baseAbsent`, where the arm's installed agent-framework doesn't bring a stretch's module or a setup's: the names of the W12 stretches, or of the setup's part (`conversations`, for `Hconv`), the run left out, each field left out where there are none;
    - `counts: {compiles, compressions, merges, quarantines}`, where `quarantines` is `{compression, merge}`, each a count or `'unreadable'`, or is `'not-reported'` when no compile reported one;
    - `usage` (`harness/lib/usage.mjs`): `kinds`, for each kind of request the stand-in answered (`agent`, `summariser`, `judge` …), `{requests, input, cacheRead, cacheWrite, output, dropped}`, the tokens as the stand-in's model of its provider counted them and the thinking blocks it dropped under the drop control, a request it refused counting nothing; for a run that writes its own history before its workload's steps, as P4's continuation and `H1b/continuation/fresh` do, `history`, the same sums for that history's requests alone; `lastDropped`, the blocks dropped from the last request the stand-in answered for the script's primary agent, not a subagent, in the workload's own steps where the run wrote its history first, or `null` where there was none; and `calibration`, the judged agent's `{multiplier, provisional, reset}` at the run's last health read, or `null` where that read gave none or failed;
  - with `--self-check`, for a run that ran, `selfCheck`: `{outcome: 'same', requests}`, `{outcome: 'differs', at, files?, detail}` or `{outcome: 'couldnt-run', reason}`.

  A run with anything in `unmeasured` or `readsFailed`, on either arm, can't be compared.

**`OUT/entries.json`**, written with `--against`, or as `OUT/after/entries.json` with `--pair`, is the head arm's differences from the base, grouped. It's a list of entries:
- `id`, a hash of the difference's kind;
- `describe`;
- `count`;
- `runs`;
- `places`, each `{run, step, digest}`;
- `examples`, one `{run, step, before, after}` for each run the entry is in, with `before` and `after` as the records' lines, their templates filled in.

`view/` merges the shares' entries in `RUNS` order.

**`OUT/reach.json`**, written with `--reach`, says which of the change's lines ran:
- `change`, the package or host the diff is of;
- `files`, each changed file's `{state, ran, notRan, couldntTell, noCode, unloaded, deletions, reason?}`:
  - `state` is `read` (a profiled host loaded a script its map names, even one in which nothing maps to code, such as a module of types alone), `not-loaded` (no profiled host loaded one) or `couldnt-tell`;
  - each list holds line numbers on the head: `notRan` is "ran in no profiled drive" (the self-check's drive, the only one read), and holds a line only when every host of every profiled drive was read and no worker or child process ran unprofiled that could have run it; `noCode` maps to no code; `couldntTell` holds only lines known to hold code; `unloaded` holds lines no read and no built map gives as code or as no code, such as a file no host loaded and no map names, or a couldn't-tell file whose lines no map places;
  - `deletions` holds `{after, state, by}` for each hunk that only deletes, after head line `after`: `reached`, `not-reached` or `couldnt-tell`, judged by the code line `by` next to it, `no-code` where no code line is on either side of it to judge it by, or `unloaded`; in a file built into more than one script, a deletion with no code line beside it in the script a host loaded is `couldnt-tell` with `by` null, and a changed line that script doesn't hold is in `couldntTell`, since another script may hold it;
  - `reason` says why a file or its lines couldn't be told;
  - a changed file that isn't script source reads `couldnt-tell`, its lines `unloaded`, with its own reason, and a binary one, which has no lines, has `binary: true`;
- `notes`, each reason that covers every line not seen to run, once each (a reason of one file's own is in its `reason`);
- `fallbacks`, `{fired, notes}`: how many times the fallback fired, and its notes, once each. It fires once for each worker or child a host started whose code the read can't follow, however many loads it holds that the scan can't follow; for each spawn the preload couldn't log; and for each line of the spawn log, or the log, that couldn't be read. A worker whose closure the scan follows isn't a firing: the files it can run read couldn't tell, with their own reason;
- `drives`, each run's boots as `{boot, read}`, `boot` being `null` for an unread entry such as a failed drive's;
- `code`, `{wrote, joined}`: the sha256 of the reach code (`harness/lib/reach.mjs` and `reach-preload.cjs`, which read hosts, shape the digests and join them) that wrote each share's digests, and of the code that joined them, so a join by another version than wrote them shows.

**`OUT/reach-digests.json`** is what joins shares: `{change, writer, changed, onDisk, split, drives, digests}`, the sha256 of the reach code that wrote it, the diff's changed lines, the code lines the built maps give those files, each changed file built into more than one script with its reason, and each boot's read digested to those files. `run/` joins every share's into the view's `reach.json`.

**Tests:**

```
npm --prefix harness ci --ignore-scripts --no-audit --no-fund --loglevel=error && npm --prefix harness test
```

The `ci` installs context-manager for `readStore`'s one test, and membrane, whose own Responses, OpenAI-compatible, OpenRouter and Bedrock adapters the stand-in's Responses and Chat Completions codecs and its Bedrock front are tested against. `harness/unit/checks-md.unit.mjs` holds `CHECKS.md`'s runs, setups, workloads, variants and numbered checks equal to the code's.

## run/: the run side

`run/context-view-run.ts` runs one pull request's view on GitHub's hosted runners and brings the records home. It runs on the house's machine, from the install, and judges nothing: the harness's head-arm `run.json` holds the comparison.

```
bun run/context-view-run.ts --repo REPO --pr N --head SHA40 --out DIR
```

`REPO` is one of `context-manager`, `agent-framework`, `membrane` or `connectome-host`.

**Before any job,** it reads the pull request, its base tip and head (into a mirror under `~/.local/state/context-view/mirrors/`), the host's `main` for a candidate the harness overlays onto the host (a connectome-host pull request's host is its own base), and the harness release named in `~/.local/state/context-view/harness` (or, to try a harness change by hand, the tip of the branch `CONTEXT_VIEW_HARNESS_REF` names). It runs nothing, and exits 3, when:
- `closed`: the pull request isn't open;
- `moved`: its head isn't `--head`;
- `doesnt-merge`: the head conflicts with the base tip;
- `needs-companion`: for a candidate the harness overlays onto the host, no stack the arms could run was found (**The stack**, below). `detail` is `{arm, package, range, wantedBy, has, why}`: the range that missed in that arm, on `package`, who asks it, and the version of `package` the arm had then (null where its `package.json` gives none). `wantedBy` is a lockfile path, `NAME@VERSION` for a release the plan chose, or null for the arm's own `package.json`. `why` is:
  - `not-plain`: the range isn't a plain semver range (an alias, a git or file spec, a dist-tag), so no release can be chosen to meet it;
  - `no-mover`: it's on an `@animalabs/*` package the plan doesn't move, or on the candidate's package, which never moves, and the package that asks isn't one the plan moves, or the arm's `package.json` gives no version;
  - `no-release`: no published release of `release` qualifies in that arm: none meets `ranges`, every range on it there, or, where `admits` is given (`{package, version}`: the candidate's package and the arm's version), none of those that meet them admits that version; with `prerelease`, a prerelease would have qualified;
  - `unsettled`: the choices for the arms came back to ones already made; `tried` is that arm's then.

  The harness would refuse an overlay that needs a release it wasn't given only after the jobs had run.

**The stack.** The harness lays the candidate's pack over connectome-host's install of its own lockfile. The plan chooses other releases there only where a range in an arm's stack misses, and only of the packages the harness lays over and records besides connectome-host: agent-framework, context-manager, membrane and chronicle, wherever the lockfile holds them at its top level with a version. It checks every range in each arm's stack on the candidate's package and on the `@animalabs/*` packages the lockfile holds at its top level with a version:
- the arm's own `package.json`'s, all three fields;
- each lockfile entry's, on the candidate's package and on each package the plan has moved, outside the root, whose spec the overlay install rewrites for every pack it lays over, and outside every copy of the candidate's package and of each moved package, and their subtrees, which the overlays replace;
- each chosen release's own, from the registry.

Where a range misses, the package it's on moves, if it's one of the four, or, where it's on the candidate's package, which never moves, the package that asks does, if it's one of the four; otherwise the plan stops. A release qualifies for an arm when it meets every range on its package there and its own range on the candidate's package admits the arm's version, and a prerelease only where the arm has a range on the package, since npm resolves a range to a prerelease only where the range admits it, which needs it to name one; a prerelease the lockfile holds moves, like any version, only where a range misses it. Of the releases that qualify for both arms it takes the lockfile's version, else the least above it, else the greatest below, for both. Where none qualifies for both, each arm whose range misses takes one the same way, and the other keeps what it has, since moving it back then could undo what the other arm's next move needs, and go round. It repeats until no range misses. Then each chosen release goes back to the lockfile's wherever that leaves the arm with no range missing: one arm at a time where the arms differ on the package, both together where they agree, by name, until none goes back. A lockfile entry under one moved package that is a copy of another is outside the stack until both have gone back, so where its ranges on a third the plan has moved, or on the candidate's package, would then miss, whichever of the two is tried second stays: which releases go back can turn on the order they're tried in, and trying them by name makes one input give one stack. connectome-host's lockfile at `cef9339` holds no `@animalabs/*` copy below its top level. The registry, `CONTEXT_VIEW_REGISTRY` or else `https://registry.npmjs.org`, is read once something moves, one document per package, so a lockfile that meets every range plans as it did before the plan could choose. The jobs pack the chosen releases from the same registry on GitHub's runners, so a `CONTEXT_VIEW_REGISTRY` must be one the runners can read too. A registry read that fails, a document that isn't JSON or gives no `versions` included, stops the run as `couldnt-run` before any job, with the base, host and harness the plan had reached. The manifest's `stack` is `{base, head}`, each the releases the plan chose for that arm by name, each `{version, host, ranges, asks?, missed?}`: the release, the lockfile's version, every range on it in the arm, as `{range, wantedBy}`, the release's own range on the candidate's package where it has one, and `missed`, `{package, range, wantedBy, has}`, the first range the lockfile's release would leave unmet in that arm, with the version it's on then. A release without `missed` is chosen only so both arms run one release, and is then the same in both. A manifest has no `stack` where nothing moved. Each job packs each chosen release (`npm pack NAME@VERSION`, from the same registry) into its arm's packs beside the candidate's, and the arm lays them all over the host. The harness still refuses an overlay that doesn't replace every copy of its package.

**Otherwise** it starts 12 jobs through on-gh at the harness release, each on its share of the runs, `--shard i/12`, and each on-gh polling its run every 2 s (`ON_GH_POLL_MS=2000`). Each job's setup mounts a tmpfs at `../m`, sized above the runner's memory and swap and with no inode limit, so no write there can fail for space before memory runs out, and the share doesn't start where its work directory isn't on such a tmpfs. The setup then starts the harness's pool for the share in the background, `run.mjs --pair --width 3` (`WIDTH`: on the runner's 4 CPUs, three drives at once took 1.52 times one drive's time and four 1.92 times, in the job-time design's probe), which balances its share by each run's three drives (`--drives 3`): the base arm's, the head arm's and the head arm's self-check. `HOME`, `TMPDIR`, the work directory, the checkpoints and the output are on the mount. Meanwhile the setup builds the two arms side by side: the base arm's shallow clone and install beside the head arm's blobless clone merged onto the base, then the base arm's build and pack beside the head arm's install, build and pack. Once all of an arm's packs are in, its companions' among them, it writes that arm's file in the pool's `--ready` directory by rename, holding the comma-separated pack paths. For connectome-host's own pull request, the head checkout is a blobless clone at `../connectome-head`, the same length as the base checkout's `../connectome-host`, since a host is driven from its checkout in place and a path it sees mustn't tell the arms apart; it's merged and installed beside the base checkout's install, and both ready files are empty. The setup also writes the diff of the change's `src/` from the base to the merged head, made in the head's merged checkout (the candidate's for an overlay, `../connectome-head` for a host change), as `../m/reach.diff`, or, when `git diff` fails, git's words as `../m/reach.diff.err`, before the head's ready file. The pool's head arm runs with `--reach ../m/reach.diff`, and `--reach-package` for an overlay, and the harness reads which of the two is there once the head is ready: a diff that can't be made never costs the head arm, which runs without reach. A setup that fails, the head's check or merge included, stops the pool. The command waits for the pool, writes its one exit code as both arms', and brings each arm's `run.json`, `summary.md`, records, reports and views home, with the head arm's `entries.json`, `reach.json` and `reach-digests.json`, the pool's log, any `failed.json` the harness wrote and any `reach.diff.err` as `reach-diff.err`, under on-gh's size bounds: views go first, then the reach files, each drop said in the evidence (`kb`, `reach-dropped`), and a reach file that can't be copied costs that share's reach, said in `reach-uncopied`, not the job.

**It writes `DIR/manifest.json`:** `repo`, `number`, `head`, `form`, `base`, `host`, `harness` (`{repo, sha}`), `stack` where the plan chose releases, `seconds` once jobs ran, `outcome`, `detail` and `shares`, with each job's arms in `DIR/share-<i>/{before,after}/`. `seconds` is `{planned, measured?}`. `planned` is the table every share planned from: each run's and each checkpoint's base-arm seconds, as the newest manifest in `STATE/views` that kept `measured` gives them, or `null` where none did, and the shares then plan from `stack.json`'s seconds alone. `measured` is this view's own base-arm seconds, each run's and each checkpoint's longest build, kept only when every share brought its base arm home. The manifest keeps them because a posted view's shares are removed once it posts. A run that ran no job writes what its reads reached, with `shares: []`. A run that comes out `ran` also writes `DIR/reach.json`, unless that write fails, which leaves the manifest written and `facts` refusing the run for the missing file: every share's `reach-digests.json` joined by the harness's `reachJoined`, in `OUT/reach.json`'s shape: a share that brought none makes every line not seen to run couldn't tell, naming the share, with git's words where its diff couldn't be made, and saying so where its reach files were dropped to keep its evidence within on-gh's bounds or couldn't be copied home, and when no share brought any, or the shares' can't be joined, it's `{couldnt}` with the reason. A run removes what an earlier run left in `DIR` before it starts.

**Exit codes and outcomes** (defined once in `run/interfaces.ts`):
- `0` `ran`: every job came home with both arms.
- `2` `couldnt-run`: a job failed (its setup, merge or install, its command, its harness, by the `why` of the `failed.json` it wrote, on-gh, or its evidence not coming home), the run side failed, it was stopped, or no harness release on this repository's `main` is named. `detail` is `{share, why}` for a job's failure, with `headNow` or `state` when the pull request moved or closed meanwhile without explaining it; `{why}` when no harness release is named, the one named isn't a commit on this repository's `main`, or the run side failed before any job; and `{why, shares}` after a stop, `shares` listing the jobs whose evidence isn't home. A usage error exits 2 with no manifest.
- `3` `arm-missing`: a job came home without an arm's `run.json`, or with the arm's harness killed by a signal. `detail` is `{share, arm, log}`, `log` being the last line of the pool's log, which the head's own code could have written. Also `3` for `closed`, `moved`, `doesnt-merge` and `needs-companion`.

**After the jobs** it reads the pull request again. A run whose only failures are head checks explained by a push or a close becomes `moved` (with `headNow`) or `closed`. Any other failure stays `couldnt-run`.

**A stop** (SIGTERM or SIGINT) asks GitHub to cancel every job still running whose run on-gh has named, then writes `couldnt-run` with the shares whose evidence isn't home. The caller owns the deadline. Each job's own limit is on-gh's, 350 minutes, under GitHub's six hours for a job.

**The harness release.** `~/.local/state/context-view/harness` names the commit every view's jobs run. `run/install-harness.ts C --go D` is its only writer: it refuses a C that isn't on this repository's `main` on GitHub, asks the release gate to install `context-view-harness` at C, and writes C only once that passes. When the release that file names isn't a commit on `main`, a run starts no job and says so, as `couldnt-run`.

## view/: the view's steps and its poll

`view/view.py` turns a run's records into the pull request's comment, and `view/poll.py` picks the next head to view. Both run on the house's machine, from the install, with the GitHub App's credentials. Their GitHub calls, the App's token and the escaping of an author's text come from review-workflow, pinned to one commit in `view/uv.lock`. Moving that pin is a change here, read like any other.

**The steps.** Each step reads one JSON object on stdin and prints one on its last line of stdout. A release's two launchers, `view/step` and `view/poll`, run `view/.venv/bin/python -I -m view` and `-m poll` from the release they're in:

```
view/step STEP < input.json
```

- `facts` `{dir, repo}`: reads `DIR/manifest.json`, as the run side wrote it, each share's `run.json` for both arms and its head arm's entries, for a run that `ran` `DIR/reach.json`, each list checked against what the harness's `reachOf` can give, and the pull request's title and description from GitHub. It writes `DIR/view.json`, the one file the reader, its check and `post` read. It refuses a manifest whose `harness` isn't this repository at a full commit, unless the run stopped as `moved` or `closed`, when nothing posts. For a candidate overlaid onto the host, it fails where an arm's `candidate.versions` doesn't give a release the manifest's `stack` names for that arm, or, for a release named for one arm alone, where the other arm didn't run the lockfile's (the entry's `host`); where an `@animalabs/*` package other than connectome-host and the candidate's differs between the arms and `stack` names it in neither; and where the arms ran one version of a package with different contents. It sees only the key packages the harness records in `candidate.versions`, each at the top level of the install: a package outside them, or a nested copy of one, it doesn't see. So no difference in a key package's top-level copy that the plan didn't choose is put on the head. `view.json`'s `differing` lists each package that does differ, `{package, base, head}`, where any does. The view knows the candidate's package by the repository's GitHub ID.
- `compared` `{dir, repo, number, head, form, base, host, harness, stack?, title, body}`: `view.json` for a change no pull request holds, such as one made to check the reader, from a harness compare run by hand. `DIR` holds the compare's two `--out` directories laid out as a view's shares, `share-<i>/{before,after}/`. From the fields given, each in the shape the run side writes it, it makes the manifest of a run that `ran` with the `share-<i>` directories there as its shares, and reads the shares as `facts` would, with `title` and `body` standing for the pull request's title and description, and `DIR/reach.json` where there is one, as the harness's `reachJoined` writes from the shares' `reach-digests.json`; without one, the comment has no reach paragraph. It writes the manifest as `DIR/manifest.json`, then `DIR/view.json` last, so a manifest that can't be written leaves no view. It asks GitHub nothing, so it refuses a repository outside the four by its name, not its ID. It refuses a `DIR` that isn't a directory, then removes what an earlier view wrote there, its `view.json`, `manifest.json`, `reader.json` and the comment's parts, before any other check, so whether it writes this view or refuses, none of those files predates it. The workflow reads what it writes only in a dry view, since its head is in no pull request.
- `post` `{dir, reader?, reads?, post?}`: posts the view's comment, one per head, in as many parts as GitHub's 65,536-character limit takes. Every word in it is fixed in `view.py`, taken from the run's manifest and records, or a head GitHub names (the pull request's head now, and the head a kept comment was first posted at), apart from the reader's account. The paragraph after its first line links `CHECKS.md` at the harness commit the view used. After the sentence on the runs' records, whether or not they differ, and the line naming any releases the arms ran differently, a paragraph says which of the change's source lines ran in no profiled drive, which files no profiled host loaded and which deletions no profiled drive reached, or that everything that could run did, and what it couldn't tell and why, in `CHECKS.md`'s words; a list longer than about three lines of the comment, or a reason longer than that, is cut, saying how much it leaves out, though a list's first item always prints whole. Whenever the paragraph cuts a list or a reason, or counts lines or deletions it doesn't name, a fold below the comment holds, file by file, every changed line and deletion not seen to run, with each reason for a line or deletion it couldn't tell, whole unless it's longer than a comment can hold, and the paragraph's last sentence points to it. The comment never points its reader at `view.json`, which only the house can open. A later head with the same result keeps the comment and edits its first line. A posting that fails partway deletes the parts of its comment the pull request then lists, and says what became of them, a delete GitHub refused included. With `post: false` it posts nothing and writes the comment beside `view.json`. It posts nothing for a `closed` or `moved` view.
- `stopped` `{repo, number, head, post?}`: posts the stopped words for a head whose run failed: one line saying the view stopped, and a link to `CHECKS.md` on `main`. It posts nothing if a whole view of that head is already there, or if the head has moved or the pull request has closed.
- `rooms` `{}`: the rooms, each with its tender, where the workflow says what isn't for GitHub, such as a reader its provider refused.

**Exit codes:** `0` with the answer on the last line. `1` with why on stderr's last line, cut at its end to 1,500 characters, since the workflow keeps a step's last 1,500 characters of stderr. `2` for a repository the App is installed on that the view doesn't cover, and for a command line that names no step; a repository the App isn't installed on fails at its token, with exit 1. `compared`, which asks GitHub nothing and so can't tell whether the App is installed, refuses any repository outside the four with exit 1.

**Run them from the install.** When its module is in the main working copy, `~/astra/context-view`, that copy's own `.venv` included, a step's command line refuses with exit 1 and the poll's with exit 2, each naming its installed form, since what they'd run there is whatever the copy holds, not the reviewed release. Another Python stops before anything acts too: at an import it can't satisfy, or, if it has review-workflow's modules, at that same refusal. A worktree outside the copy runs its own code.

**The poll** is a Jobs job's condition:

```
view/poll --job
```

- **What it prints:** at most one line, `{"key", "args"}`, while no view's run is unsettled when it lists them: again the line it printed before, while Jobs hasn't taken it and its head still waits, or else one for the open pull request head that has waited longest. The listing isn't a lock, so a view started by hand between it and Jobs' start runs beside the one Jobs starts. `args` is `{repo, number, head}`, the step input the workflow starts with.
- **Which heads:** while its pull request stays open, never a head it had when the poll first saw its repository, so such a pull request gets its first view at its next push, and never one whose view has run, an ask's view included. A pull request that a pass finds closed is new to the poll if it reopens, so its head gets a view, unless the workflows store still holds a run of that head's view (it clears a settled run a week after it settles). A draft waits until it's marked ready.
- **Exits:** `0` with a line, `1` with none, `2` on a failure, said on stderr.
- **State:** `~/.local/state/context-view/poll.json`, under its own lock. Jobs' cursor says which line it took.
- **Without `--job`,** as when it's run by hand to check it, a pass prints what it would and changes nothing: it keeps no line, queue or `seen`, gives no cursor and puts no 👀 on a comment. A line is out only because a job will take it, so only a job's pass puts one out.

**Its asks step** is another job's condition, a view of a pull request asked for by a comment:

```
view/poll asks --job
```

- **An ask:** a comment on a pull request in a covered repository whose text, leading blank lines aside, starts with a line holding `/context-deltas` alone, by an account in `poll.py`'s `ASKERS` that GitHub gives write access, and not the App's own. A repository's first pass starts from then, so no comment before it asks. A permission GitHub doesn't answer fails the pass, so the comment is read again.
- **What it prints:** the same line as the views' poll, under the same one-view-at-a-time rule, for each ask in the order the asks were made: `args` is the pull request's head as GitHub gives it in the pass that prints the line, and the key is that head's view key with `:ask-<comment id>` after it, so an earlier view of that head doesn't stand in for the ask. A newer ask on a pull request takes the place of one still queued there, and of its line where that's out and not yet taken.
- **👀:** each ask queued gets it, meaning a view is coming, unless GitHub refuses it or the call fails, which is said on stderr. An ask leaves the queue once Jobs takes its line. A start that fails leaves Jobs' cursor where it was, so the line prints again.
- **An ask that waits or goes:** one whose repository a pass doesn't list, or whose pull request GitHub doesn't answer for when its line would print, waits, said on stderr, and the next ask prints in its place; a pull request GitHub doesn't answer for as its ask is taken in fails the pass, so the comment is read again. One whose pull request is closed, or that GitHub has no pull request for, is said on stderr and gets no view. A push before its view's runs finish ends the view as `moved`, posting nothing; one after them still posts the view of the head its line named, saying the pull request's head has since moved. Asking again views the new head.
- **Both steps:** a line either step has printed holds the other step until a run under its key shows in the workflows store, so one view at a time holds across the two jobs. A paused job's line holds the other step until the job resumes and takes it.
- **Why a step's line ends at its own next pass after Jobs takes it:** by then that line's run is in the store, unless its job stays paused, before its next condition, past the week the store keeps a settled run. Jobs adopts a condition's cursor only once its action succeeds, or once whoever holds an action whose effect was unknown confirms, with evidence, that it took effect (astra-jobs' `adoptFrozen`, reached from the success branch in `src/store/outcomes.ts` and from `effect_confirmed` in `src/store/control.ts`), and the workflow action succeeds only once `startHouse` has made its runs (workflow-house's `src/provider.ts`). A job runs one occurrence at a time, so its next condition comes after.
- **State:** the `asks` part of the same file, with its own line and queue, sharing only the App's tokens with the views'. Its job's own cursor says which line it took.

**The build.** The promote's `prepare` runs `bash view/build.sh STAGE`. It syncs `STAGE/view/.venv` from `uv.lock` with `--locked`, and installs the view itself, not a link to it. It builds only review-workflow and the view: every package from the index must come from one of its wheels, and a lock that would have one built instead is refused. It refuses if a `.py` or `.pth` file in the environment names the stage's path, and it imports `view`, `poll` and `pr_review` with the stage's interpreter and runs each launcher with `--help` before anything switches to the release.

**Tests:**

```
(cd view && UV_NO_BUILD=0 uv run --frozen python -m unittest discover -q)
```

The tests use their own stand-ins for GitHub, for the house's Commons and for `astra-workflows`. `test_build` runs `build.sh` on stages of its own, with uv's cache.
