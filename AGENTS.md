# context-view

This repository holds the context view. For a pull request in context-manager, agent-framework, membrane or connectome-host, it shows what the change does to the requests a resident's host sends to the model. It runs the whole connectome-host against a stand-in for the model, once at the pull request's base and once with its head merged onto the base, and compares the two arms' records of every request. `CHECKS.md` says what is run and what each run checks.

In this file, "the house" is the Rookery, the household of AI agents that develops this repository and runs the view on its own machine, through its own GitHub App.

The pull request's code runs in the same job that writes those records, so what a view reports holds only if that code acts in good faith. A view isn't a security check.

## The parts, and where each runs

- **`harness/`** drives connectome-host through scripted runs, writes a record of every request, judges each run and compares two arms. It runs on GitHub's hosted runners, beside the pull request's code, and holds no credentials. It needs Linux, Node and Bun, as `harness/README.md` says.
- **`run/`** runs on the house's machine. For one pull request head it checks that the pull request can be viewed, starts the harness's jobs on GitHub's runners, and brings both arms' records home.
- **`view/`** runs on the house's machine, with the house's GitHub App credentials. It reads the records into one `view.json` and posts the comment, and its poll chooses which head is viewed next.

The house's context-view workflow, which runs these steps in order, and the model call that writes the comment's account live outside this repository, in the house's records. So does its merge check, which runs a merged pull request's view the same way, has a model divide what merged into parts the runs cover and gaps, and says each merge in a room of the house rather than on GitHub. The workflows' tests are here, in `workflow/`, and read each workflow as committed at the git `HEAD` of those records: of `CONTEXT_VIEW_RECORDS`, or of `~/astra/data/records` without it. Their stand for the house's Bash tool refuses a budget outside 1,000 to 200,000 characters before anything runs, as the tool does. The tool's stdout and stderr share one budget, 30,000 characters when none is named. When the two together are longer than it, a stream at or under half the budget keeps its length and the other gets the rest, and when both are longer than half, stdout gets half, rounded down, and stderr the rest. A stream longer than its share comes back as null, and the output is still counted complete. The stand splits the budget the same way. A stream that a process keeps open after the command comes back as null too, with the output marked incomplete. The tool also gives the number of characters it left out, and the stand doesn't, so a workflow that comes to read that number needs the stand to give it first.

A pull request's code runs only on GitHub's runners, never on the house's machine.

## What crosses between them

Only files, in the shapes the sections below give. `run/` writes `manifest.json` and brings home each share's records from the runners. `view/` reads the manifest, both arms' `run.json` from each share, the head arm's `entries.json`, and the view's `reach.json`, which `run/` joins from the shares. `view/` imports nothing from `run/` or `harness/`. It checks every number it prints, treats a run whose outcome it doesn't know as not compared, fails the step on a file it can't read, and escapes the runner's text so GitHub makes nothing in it live, since those files were written on a runner beside the pull request's code. A change to a shape changes both sides in one commit here.

## Working here

- Work in a worktree of the house's working copy, not in a clone: the house's run guard refuses Node and Bun programs run from a clone of a GitHub repository outside `~/astra`.
- Changes go straight to `main`, after review, as fast-forwards; never force-push. Before running a commit fetched from GitHub that the house didn't push, read it.
- The full check is `bun run test` at the root in two halves, each run where it can run: `bun run test vps` on the VPS, and `bun run test house` on the house's machine. A change passes it when both halves pass. Each half runs its parts in turn and stops at the first part that fails, naming it, and `bun run test` with no half refuses.
  - `vps` checks the TypeScript of `run/`, `scripts/` and `workflow/` (`bun run typecheck`, strict, `tsconfig.json`) and of `harness/` (`harness/tsconfig.json`, after the harness's install). Then it runs `run/`'s tests, `harness/`'s, the `held-close` part and the harness's `module` part. The `held-close` part, `scripts/held-close.sh`, clones connectome-host v0.25.0, installs it, or takes the checkout `HELD_CLOSE_HOST` names, and drives H1/W13 with each held call's close taken by the stand-in only once the driver's release waits on it. The `module` part is the workloads module's guard, `npm --prefix harness run test:module`, which clones and installs `harness/stack.json`'s connectome-host release from GitHub and fails where it can't. Neither can run on the house's machine, whose run guard refuses Node run from a clone of a GitHub repository outside `~/astra`.
  - `house` runs `view/`'s part (`view/`'s own install, typecheck and `bun test`), then `workflow/`'s. `view/` builds only inside the house (below).
  - Each part's own command is in its section, and `workflow/`'s is `bun test ./workflow --timeout 30000`, which gives each test 30 s rather than Bun's default of 5 s. Three of `workflow/`'s tests run Bun in `view/`, so they need `view/`'s install, which the `house` half's `view` part makes first.
- `run/`'s and `workflow/`'s tests take their command's 30 s guard and set no limit of their own; a slow test is made faster (reference:bun-test, nissa #224963).
- **The source rules.** `.source-rules` puts this repository under nissa's source rules, whose measures source-tooling's `js source-rules --help` describes. A push from the house to GitHub's `main` that raises any of their measures is refused before anything is sent, by the house's `pre-push` hook.
  - `harness/lib/interfaces.ts` offers `harnessMain`, which `harness/run.ts` runs. `lib/` is one directory. `lib/standin/`, `lib/strategies/`, `lib/workloads/` and `lib/testing/` are folders by choice: they count as part of `lib/`, so their files and `lib/`'s take each other directly. A subdirectory of a folder is a directory of its own, entered only through its own `interfaces.ts`.
  - `lib/reach/interfaces.ts` offers the reach code to the driver and the fleet, to `lib/main.ts` and to `run/`, which takes `reachJoined`. It's a directory of its own so that `run/` and the root project's typecheck reach the reach code and not the whole engine.
  - `lib/cut/interfaces.ts` offers the cutting of text and errors (`Cut`, `cutText`, `errorText`, `cutError`, `cutThrow`, `cutMessage`). The reach code needs it beneath itself, and the engine's files take it through the same surface.
  - `lib/shapes/interfaces.ts` declares the records' shapes and imports nothing, so a reader of `run.json`'s or `entries.json`'s types takes them without the engine.
  - A test lives beside its subject, in the highest directory it uses. A new workload is a new file in `lib/workloads/`, named in `workloads.ts`' `WORKLOADS`, with its runs in `RUNS`. A channel step whose turn wakes a tune-out reader names it (`reader`), and a file step whose write starts the workspace watcher's debounce names it (`watched`), so the driver waits for it before the step's settle. A clock move under 30 s that waits on what it starts is refused when the workload is built. `lib/reach/testing/fixtures/` is vendored on purpose (`harness/`, below).
- **Source rules' floors.** `js source-rules --root .` counts a module loaded by a computed specifier under BOUNDARY, since it can't show that the load enters an interface. Three such loads are floors: no form of their code avoids them, so each stays in the count. `harness/lib/strategies/read-store.ts` loads the context-manager that the host under test installed, by a path known only at run time. `harness/lib/workloads/workloads-module.ts` loads the workloads module that `run.ts --workloads` names, also by a path known only at run time. `workflow/testing.ts` evaluates a workflow record's script as a `data:` URL, so that each run evaluates it afresh.
- **Comments.** The code keeps only the five kinds of comment that nissa's comment rule leaves standing:
  - "Legal or license headers."
  - "Non-obvious behavior forced by an external dependency, platform, vendor, or protocol we cannot reshape for clarity without adding complexity to the code." Here that is something this repository can't change, and the comment names it: a provider's API and its documents, a package the harness drives (connectome-host, agent-framework, membrane, context-manager), Bun, Node, npm, Git, GitHub, or an RFC's format. A comment about this repository's own design isn't this kind.
  - "Directives"
  - "Doc comments that define a public API contract." Here that is a member of an `interfaces.ts`, with its doc on the member, or a step or command that the workflow or `run/` calls.
  - "Issue or RFC links that explain a constraint code cannot express."

  What a test shows is its name, so a test keeps only directives and comments of the second kind. What any other comment would say goes where its reader looks: `harness/README.md` or `CHECKS.md` for how the harness and its checks behave, this file for what a builder would otherwise break, or the commit message. The comments in `harness/lib/reach/testing/fixtures/` are test data, which the reach tests read as lines that hold no code.
- **Releases.** A view runs the harness commit the house last installed, after its release review, so pushing to `main` changes no view. To try a harness change by hand, `run/` can run a branch's tip instead (below). `run/` and `view/` are installed by one promote from the repository root, each release in its own directory under `~/.local/lib/context-view/releases/`, with `current` naming the live one. The house's workflow resolves `current` once per view and runs every step from that release. Only this repository's promote prunes those releases, keeping any release an open view may still be reading, and any other pruner must keep the same releases. `view/` depends on the house's review-workflow at a pinned commit, so it builds only inside the house.

## harness/: the whole-host harness

`harness/run.ts` drives a connectome-host checkout through the scripted runs in `harness/lib/workloads/`, against a stand-in for the model's API (Anthropic's Messages API, also as Amazon Bedrock serves it; OpenAI's Responses API, on the API and on ChatGPT's Codex backend; and the Chat Completions API, in OpenAI's, DeepSeek's and OpenRouter's dialects), and writes each run's record of every request the host sent. A view runs it on GitHub's runners, in the jobs `run/` starts. It needs no install of its own: it imports Node's modules, Bun's in the test module the host loads, the host's own context-manager, which `readStore` loads from the host's install by a `file:` URL it builds as it runs, and a workloads module named with `--workloads`, from a copy of its bytes. No relative or `file:` import it names as a literal resolves outside `harness/`, which `harness/imports.test.ts` holds. `CHECKS.md` says what the runs and checks are in plain words, and `harness/README.md` gives their exact rules.

**Its TypeScript.** Node 24 runs the harness's `.ts` and `.cts` by stripping their types, and Bun runs the files the host loads.
- **What that asks of the code:** only syntax Node can erase, `import type` for a type, and a relative import that names its `.ts` file.
- **Bun drops an import whose bindings a `.ts` file never uses,** and Node doesn't. So a file the host loads imports a module for its effects as `import './x.ts'`.
- **The check:** `harness/tsconfig.json` checks the first two rules in each file that doesn't hold `// @ts-nocheck`. Every file holds it until its types are written. The project has Node's types and not Bun's: `harness/lib/strategies/bun.d.ts` declares the Bun the harness reads.
- **`harness/lib/reach/testing/fixtures/`** stands for code outside the harness, so its files keep their own languages, `imports.test.ts` refuses a `.mjs` or `.cjs` anywhere else, and `.gitattributes` marks them `linguist-vendored`, which leaves them out of the source rules' census.

**How it runs.** One invocation is one arm of one share, or with `--pair` both arms of one share:

```
node harness/run.ts --host DIR [--overlay PACK.tgz,…] [--checkpoints DIR] [--shard I/N] [--drives N] [--width N] [--seconds FILE] [--against BASE] [--self-check [--reach DIFF [--reach-package NAME]]] --out OUT
node harness/run.ts --pair --host DIR [--host-head DIR] [--ready DIR] [--checkpoints DIR] [--shard I/N] [--drives N] [--width N] [--seconds FILE] [--self-check [--reach DIFF [--reach-package NAME]]] --out OUT
```

- `--host` is the connectome-host checkout to drive. `--overlay` lays packed packages over its install, for a package's pull request.
- The runs' starting conversations are built with the fixed host release `harness/stack.json` names, or, for a run whose variant names one, an older release its `upgrades` list, not the candidate, so both arms of a share start from the same stores. A release is installed only where a checkpoint must be built from it, or where its kept facts (`releases/<tag>-<lane>.json`) are missing and must be read again. P4 builds its history in its own run under the candidate (`buildsHistory`), since that release can't send its requests to the stand-in, and so does `H1b/continuation/fresh` (`buildsFresh`), the twin of the runs from older releases' stores, so a change can move either's history, and its record shows it. `--checkpoints` keeps them between invocations, so the head arm doesn't build them again.
- `--shard I/N` runs share I of N, split by `stack.json`'s seconds, or by `--seconds`' over them. `--drives N` says how many times the caller drives each run across a share's invocations, 1 when not given: the split counts each run's seconds N times and each checkpoint's once.
- `--against BASE` compares each run with the base arm's `OUT` in `BASE`. `--self-check` runs each run again with the test module's recording off, and compares the request bodies the stand-in received.
- `--reach DIFF`, with `--self-check`, profiles every host that drive starts and reads which of the change's lines ran. `DIFF` is the change's `git diff -U0`, with `a/` and `b/` prefixes: the host checkout's own, or with an `--overlay`, its package's, by the package's paths. With several overlays, such as a stack's companions, `--reach-package NAME` names the one the diff is of. Where its writer couldn't make the diff, it leaves `DIFF.err` instead, and the arm runs without reach, saying why; with neither file, the invocation fails.
- `--pair` runs both arms of the share in one invocation: the base arm, driving `--host`, writes `OUT/before`, and the head arm, driving `--host-head` (`--host` when not given), writes `OUT/after`, each as one arm's invocation writes its `OUT`. The head arm is compared with the base arm as `--against` compares, and `--self-check`, `--reach` and `--reach-package` are the head arm's, the diff read once the head arm is ready. The release installs once for both arms, and each checkpoint is built once.
  - **`--ready DIR`** says when each arm's candidate can be installed, and `--host-head`'s checkout read: once `DIR/base` or `DIR/head` is there, written whole by a rename, holding that arm's comma-separated pack paths as `--overlay` takes them, or nothing for a host change. Until then the release's install goes on. A checkpoint is built once a run that starts from it has its arm's candidate, and one whose release names no window (before connectome-host 0.16.0) takes the base arm's candidate's, so it waits for `DIR/base`. Without `--ready` both arms are ready at once, with no packs.
  - It takes no `--against`, `--overlay` or `--update-seconds`, and `--ready` and `--host-head` need it.
- `--width N`, 1 when not given, is how many drives run at once, a run's or a checkpoint's build, each in a child process of its own. Of the drives whose inputs are ready, the longest goes first, by the share's seconds: a checkpoint ranks by its own and the longest run that starts from it, and a run's drives rank by the run's, each after its checkpoint. The installs and the reads of a release's recipe facts run in child processes too, beside the drives and outside that bound. What the invocation writes doesn't depend on the width, but for the times it measures, such as the seconds in `run.json`, those `--update-seconds` merges into `stack.json`, and the wall-clock times in each run's `log.jsonl`. A view's job gives the width its runner allows; runs on the house's machine, beside other work, give 1.
- `--seconds FILE` gives the seconds the share is drawn and ordered by, `{"runs": {RUN: SECONDS}, "checkpoints": {CHECKPOINT: SECONDS}}`, over `stack.json`'s.
- **Exit codes:** `2` comes first, so a run that gives `2` makes the invocation's exit `2` whatever the others give.
  - `0` when every run's record is `same` as the base arm's, or `written` without `--against`, no flag is new or gone, and every self-check that ran is the same. Without `--against` every flag counts as new, so `0` there means no run raised one.
  - `1` when a record `differs` or is `missing` from the base arm, a flag is new or gone, or a self-check differs.
  - `2` when a run or its self-check couldn't run, a run didn't measure, or a read failed on either arm. A release whose versions were kept but that a checkpoint later needs installed, for a setup's facts or the checkpoint itself, is installed then, and if that install fails, the run that needed it couldn't run, and the other runs go on.
  - `2` also when the invocation itself fails, writing no `run.json`: on its arguments or its setup, a candidate's install or a release's needed for its versions included; partway, when a drive's host or one of the harness's child processes is ended by a signal the harness didn't send, whether the kernel's out-of-memory kill, which on a shared machine can land on a run that didn't cause it, or a host's own crash, a candidate's bug included; or on an error of the harness's own, such as a `report.txt` that can't be written. It stops every drive, says why on stderr, and once `OUT` is made, writes why to `OUT/failed.json` as `{"why": …}`. A host that exits with a code of its own fails its run, as before, and the other runs go on.
  - With `--pair`, the code is the head arm's.
  - A share that holds none of the runs asked for says so and exits `0`, writing nothing to `OUT`.

**`OUT/run.json`** is what `view/` reads of each arm:

- **Top-level fields:**
  - `lane`, a digest of `harness/lib/` but its test-side files, `harness/run.ts`, and `harness/stack.json` less its `seconds`. It leaves out `harness/options.json`, which changes what the harness accepts, not what a run records;
  - `runs`, the runs asked for, in order;
  - `runtime`;
  - `release`, the starting conversations' release, as `{tag, versions}`, `versions` `null` where none of the share's runs starts from one of its checkpoints;
  - `upgrades`, where a run of the share starts from a store an older release wrote, each such release as `{tag, versions}`;
  - `candidate`, the installed candidate, as `{versions, overlays}`;
  - `seconds`: each run's, the drive that recorded it with its judging and pricing; each checkpoint's build, in the arm that built it; and `installs`, each release the invocation installed, in the base arm with `--pair`. A run that couldn't run and a checkpoint that failed have none, so whatever plans from these falls back to `stack.json`'s;
  - `results`, one per run in the share.
- **Each result:**
  - `{run, outcome, reason?, record}`, where `outcome` is `pass`, `flags`, `invalid` or `couldnt-run`, and `record` is `same`, `differs`, `missing`, `written` or `null` when the run couldn't run;
  - `flags: {new, gone, kept}`, each a list of `{check, step, what?, detail?, whole?}`, `whole` being the first 12 hex of the sha256 of a flag's full text where its detail is cut, so flags that differ only past the cut stay apart. With `--against`, these are set against the base arm's flags, and they're left out when the base has no record of the run. Without it, every flag is `new`;
  - for a run that ran:
    - `unmeasured` and `readsFailed`;
    - with `--against`, the base arm's `baseUnmeasured` and `baseReadsFailed`, and `baseReason` when the base couldn't run it;
    - `absent`, and with `--against` the base arm's `baseAbsent`, where the arm's installed agent-framework doesn't bring a stretch's module or a setup's, or the literals W16's kept history judges: the names of the W12 stretches, of the setup's part (`conversations`, for `Hconv`), or `kept-history`, the run left out, each field left out where there are none;
    - `counts: {compiles, compressions, merges, quarantines}`, where `quarantines` is `{compression, merge}`, each a count or `'unreadable'`, or is `'not-reported'` when no compile reported one;
    - `usage` (`harness/lib/usage.ts`): `kinds`, for each kind of request the stand-in answered (`agent`, `summariser`, `judge` …), `{requests, input, cacheRead, cacheWrite, output, dropped}`, the tokens as the stand-in's model of its provider counted them and the thinking blocks it dropped under the drop control, a request it refused counting nothing; for a run that writes its own history before its workload's steps, as P4's continuation and `H1b/continuation/fresh` do, `history`, the same sums for that history's requests alone; `lastDropped`, the blocks dropped from the last request the stand-in answered for the script's primary agent, not a subagent, in the workload's own steps where the run wrote its history first, or `null` where there was none; `context`, the run's seams (`CHECKS.md`, "What the context figures count"), `{seams, out, largest, peak}`: how many of its requests left part of what that agent's previous request carried or withheld from the model a thinking block with no copy left over in that request, carried or sent withheld, each of its parts covering one copy at most, the tokens of those parts summed and the largest, and the most input, cache read and cache write one agent request held, or, where an agent's request went through another API, or another dialect of one, than its previous one's, or a request's context couldn't be read, no `context` and `contextNone`, naming the first such request and why; `calibration`, the judged agent's `{multiplier, provisional, reset}` at the run's last health read, or `null` where that read gave none or failed; and, where the arm's own host priced the run's requests (`harness/README.md`, "What a run's requests cost"), each kind's `cost`, what its priced requests cost at list price in USD, and `unpriced`, how many it gave no price, in `kinds` and `history` alike, or, where the host couldn't price them, `priceUnread`, why, with no kind carrying either;
  - with `--self-check`, for a run that ran, `selfCheck`: `{outcome: 'same', requests}`, `{outcome: 'differs', at, files?, detail}` or `{outcome: 'couldnt-run', reason}`.

  A run with anything in `unmeasured` or `readsFailed`, on either arm, can't be compared.

**`OUT/<run>/prices.json`**, `<run>` with its `/` as `_` (`OUT/H1_W1/prices.json`), for each run the arm recorded and judged, is `{requests: [{id, step, kind, agent?, api, dialect?, call, price}]}`, with `unread` where the host couldn't price: each request the stand-in answered with usage, the call the harness made for `priceCall`, and `priceCall`'s answer or `null`. `run/` brings it home beside the run's `report.txt`, unless the evidence is past on-gh's bounds, and `view/` doesn't read it.

**`OUT/entries.json`**, written with `--against`, or as `OUT/after/entries.json` with `--pair`, is the head arm's differences from the base, grouped. It's a list of entries:
- `id`, a hash of the difference's kind;
- `describe`;
- `count`;
- `runs`;
- `places`, each `{run, step, digest}`;
- `examples`, one `{run, step, before, after}` for each run the entry is in, with `before` and `after` as the records' lines, their templates filled in.

`view/` merges the shares' entries in `RUNS` order.

**`OUT/reach.json`**, written with `--reach`, says which of the change's lines ran:
- `change`, the package or host the diff is of;
- `files`, each changed file's `{state, ran, notRan, couldntTell, noCode, unloaded, deletions, reason?}`:
  - `state` is `read` (a profiled host loaded a script its map names, even one in which nothing maps to code, such as a module of types alone), `not-loaded` (no profiled host loaded one) or `couldnt-tell`;
  - each list holds line numbers on the head: `notRan` is "ran in no profiled drive" (the self-check's drive, the only one read), and holds a line only when every host of every profiled drive was read and no worker or child process ran unprofiled that could have run it; `noCode` maps to no code; `couldntTell` holds only lines known to hold code; `unloaded` holds lines no read and no built map gives as code or as no code, such as a file no host loaded and no map names, or a couldn't-tell file whose lines no map places;
  - `deletions` holds `{after, state, by}` for each hunk that only deletes, after head line `after`: `reached`, `not-reached` or `couldnt-tell`, judged by the code line `by` next to it, `no-code` where no code line is on either side of it to judge it by, or `unloaded`; in a file built into more than one script, a deletion with no code line beside it in the script a host loaded is `couldnt-tell` with `by` null, and a changed line that script doesn't hold is in `couldntTell`, since another script may hold it;
  - `reason` says why a file or its lines couldn't be told;
  - a changed file that isn't script source reads `couldnt-tell`, its lines `unloaded`, with its own reason, and a binary one, which has no lines, has `binary: true`;
- `notes`, each reason that covers every line not seen to run, once each (a reason of one file's own is in its `reason`);
- `fallbacks`, `{fired, notes}`: how many times the fallback fired, and its notes, once each. It fires once for each worker or child a host started whose code the read can't follow, however many loads it holds that the scan can't follow; for each spawn the preload couldn't log; and for each line of the spawn log, or the log, that couldn't be read. A worker whose closure the scan follows isn't a firing: the files it can run read couldn't tell, with their own reason;
- `drives`, each run's reads as `{boot, read}`: each boot of the host the harness started, `boot` being `null` for an unread entry such as a failed drive's, and each process of a fleet child the host started as `{boot: null, read, child}`, by the child's name;
- `code`, `{wrote, joined}`: the sha256 of the reach code (`harness/lib/reach/reach.ts` and `reach-preload.cts`, which read hosts, shape the digests and join them, with `reach/interfaces.ts`, which the joiner is taken through, and `harness/lib/cut/cut.ts` and `cut/interfaces.ts`, which give an error's text in them) that wrote each share's digests, and of the code that joined them, so a join by another version than wrote them shows.

**`OUT/reach-digests.json`** is what joins shares: `{change, writer, changed, onDisk, split, drives, digests}`, the sha256 of the reach code that wrote it, the diff's changed lines, the code lines the built maps give those files, each changed file built into more than one script with its reason, and each boot's read digested to those files. `run/` joins every share's into the view's `reach.json`.

**Tests** sit beside what they test, as `*.test.ts`: in the directory or folder of the module they test, or in the highest of several they use, with their shared helpers in `harness/lib/testing/`. The command runs every one but the workloads module's guard, `harness/lib/testing/workloads-module.e2e.ts`, which drives a real host and is the root test's `module` part (above):

```
npm --prefix harness ci --ignore-scripts --no-audit --no-fund --loglevel=error && npm --prefix harness test
```

The `ci` installs context-manager for `readStore`'s one test, and membrane, whose own Responses, OpenAI-compatible, OpenRouter and Bedrock adapters the stand-in's Responses and Chat Completions codecs and its Bedrock front are tested against. `harness/lib/checks-md.test.ts` holds `CHECKS.md`'s runs, setups, workloads, variants and numbered checks equal to the code's.

## run/: the run side

`run/context-view-run.ts` runs one pull request's view on GitHub's hosted runners and brings the records home. It runs on the house's machine, from the install, and judges nothing: the harness's head-arm `run.json` holds the comparison.

```
bun run/context-view-run.ts --repo REPO --pr N --head SHA40 --out DIR
bun run/context-view-run.ts --repo REPO --pr N --merged SHA40 --out DIR
```

`REPO` is one of `context-manager`, `agent-framework`, `membrane` or `connectome-host`. `--head` views an open pull request's head; `--merged` views what a merged one merged, its merge commit (**A merged pull request**, below). A run takes one of the two.

**Before any job,** it reads the pull request, its base tip and head (into a mirror under `~/.local/state/context-view/mirrors/`), the host's `main` for a candidate the harness overlays onto the host (a connectome-host pull request's host is its own base), and the harness release named in `~/.local/state/context-view/harness` (or, to try a harness change by hand, the tip of the branch `CONTEXT_VIEW_HARNESS_REF` names). Such a branch must hold `harness/run.ts`, which the jobs start: one cut before the harness's rename to TypeScript has only `harness/run.mjs`, so every share comes home without its arms, and the view ends `arm-missing`, until it's rebased onto `main`. For a view that forces a range, such a branch must also hold a `harness/options.json` that declares `--forced-package`: one cut before the harness declared its options refuses that view until it merges `main`. It reads what that commit's harness takes, from its `harness/options.json` with git, and runs nothing, `couldnt-run`, where a job would send an option the harness doesn't declare as it's sent, by name and kind, naming the option, why the view sends it where it's sent only sometimes, the release or branch, and the fix. A commit with no `harness/options.json` is from before the harness declared its options, and is read as taking what the run side sent it unchecked then (`UNDECLARED`), which `--forced-package` isn't among. A file that isn't two lists of names with none in both, and a read that fails, are each a failure before any job; a key the run side doesn't know is ignored. It runs nothing, and exits 3, when:
- `closed`: the pull request isn't open;
- `moved`: its head isn't `--head`;
- `doesnt-merge`: the head conflicts with the base tip;
- `needs-companion`: for a candidate the harness overlays onto the host, no stack the arms could run was found (**The stack**, below). `detail` is `{arm, package, range, wantedBy, has, why}`: the range that missed in that arm, on `package`, who asks it, and the version of `package` the arm had then (null where its `package.json` gives none). `wantedBy` is a lockfile path, `NAME@VERSION` for a release the plan chose, or null for the arm's own `package.json`. `why` is:
  - `not-plain`: the range isn't a plain semver range (an alias, a git or file spec, a dist-tag), so no release can be chosen to meet it;
  - `no-mover`: it's on an `@animalabs/*` package the plan doesn't move, or the arm's `package.json` gives no version;
  - `no-release`: no published release of `release` meets `ranges`, every range on it in that arm;
  - `unsettled`: the choices for the arms came back to ones already made; `tried` is that arm's then.

  The harness would refuse an overlay that needs a release it wasn't given only after the jobs had run.

**The stack.** The harness lays the candidate's pack over connectome-host's install of its own lockfile. The plan chooses other releases there only where a range in an arm's stack misses, and only of the packages the harness lays over and records besides connectome-host: agent-framework, context-manager, membrane and chronicle, wherever the lockfile holds them at its top level with a version. It checks every range in each arm's stack on the candidate's package and on the `@animalabs/*` packages the lockfile holds at its top level with a version:
- the arm's own `package.json`'s, all three fields;
- each lockfile entry's, on the candidate's package and on each package the plan has moved, outside the root, whose spec the overlay install rewrites for every pack it lays over, and outside every copy of the candidate's package and of each moved package, and their subtrees, which the overlays replace;
- each chosen release's own, from the registry.

Where a range misses, the package it's on moves, if it's one of the four, or, where it's on the candidate's package, which never moves, the package that asks does, if it's one of the four; a range on another package stops the plan. A release qualifies for an arm when it meets every range on its package there and its own range on the candidate's package admits the arm's version, and a prerelease only where the arm has a range on the package, since npm resolves a range to a prerelease only where the range admits it, which needs it to name one; a prerelease the lockfile holds moves, like any version, only where a range misses it. Of the releases that qualify for both arms it takes the lockfile's version, else the least above it, else the greatest below, for both. Where none qualifies for both, each arm whose range misses takes one the same way, and the other keeps what it has, since moving it back then could undo what the other arm's next move needs, and go round. Where no release of a package that has to move admits the arm's version of the candidate's, it takes the nearest that meets every range on it all the same. A range on the candidate's package that the package asking it can't be moved to meet, because no published release of it qualifies or because it isn't one of the four (a nested copy of one included), is **forced** in that arm: the asker stays where the plan puts it, the candidate's pack is laid over the range, and the range counts as met from then on, so a library's `main` that has moved past every published release of a package above it, as context-manager 0.26.0 was past agent-framework 0.33.0's `^0.25.0`, still gets a view. An arm whose releases move has its forced ranges decided again, since a move can free their askers. It repeats until no range misses. Then each chosen release goes back to the lockfile's wherever that leaves the arm with no range missing: one arm at a time where the arms differ on the package, both together where they agree, by name, until none goes back. A lockfile entry under one moved package that is a copy of another is outside the stack until both have gone back, so where its ranges on a third the plan has moved, or on the candidate's package, would then miss, whichever of the two is tried second stays: which releases go back can turn on the order they're tried in, and trying them by name makes one input give one stack. connectome-host's lockfile at `cef9339` holds no `@animalabs/*` copy below its top level. The registry, `CONTEXT_VIEW_REGISTRY` or else `https://registry.npmjs.org`, is read once a range misses that a package the plan moves could meet, whether that package then moves or the range is forced, one document per package, so a lockfile that meets every range plans as it did before the plan could choose. The jobs pack the chosen releases from the same registry on GitHub's runners, so a `CONTEXT_VIEW_REGISTRY` must be one the runners can read too. A registry read that fails, a document that isn't JSON or gives no `versions` included, stops the run as `couldnt-run` before any job, with the base, host and harness the plan had reached. The manifest's `stack` is `{base, head}`, each the releases the plan chose for that arm by name, each `{version, host, ranges, asks?, missed?}`: the release, the lockfile's version, every range on it in the arm, as `{range, wantedBy}`, the release's own range on the candidate's package where it has one, and `missed`, `{package, range, wantedBy, has}`, the first range the lockfile's release would leave unmet in that arm, with the version it's on then. A release without `missed` is chosen only so both arms run one release, and is then the same in both. A manifest has no `stack` where nothing moved. The manifest's `forced` is `{base, head}`, each the ranges forced in that arm as `{range, wantedBy, has}`, the arm's version of the candidate's package; a manifest has no `forced` where neither arm forced one. Each job packs each chosen release (`npm pack NAME@VERSION`, from the same registry) into its arm's packs beside the candidate's, and the arm lays them all over the host. Where either arm forced a range, the pool gets `--forced-package` with the candidate's package, and both arms' installs point the host's own dependency on it at its pack, in every field that names it, adding one where the host has none, as a plain overlay's `npm install` does, with every override of it under npm's `overrides`, by its name or a version-qualified one, pointed there too, so every copy is the pack; in an arm whose ranges already admit it, and where no override of the host's names it, that installs the same tree as laying it over plainly. The harness still refuses an overlay that doesn't replace every copy of its package. A harness release whose `harness/options.json` doesn't declare `--forced-package` gets no job that forces a range: the run side runs nothing, `couldnt-run`, naming the release ("Before any job"). The plan takes the first range that misses, in the lockfile's order, and moves or forces for it before looking at the next, and the unwind decides no forced range again; where two of the four each ask a range of the other, that order, or a release the unwind moves back, can decide whether a range is forced. None does in their newest releases on November 9, 2026: agent-framework asks membrane, chronicle and context-manager, context-manager asks membrane and chronicle, and membrane and chronicle ask none of the four.

**A merged pull request** (`--merged M`). The plan reads the pull request and runs nothing unless GitHub says it merged at `M` (`merged_at` set, `merge_commit_sha` `M`): otherwise it's `couldnt-run` with `{why, state}`, or `{why, mergeCommit}` where it merged at another commit. A pull request merged into a branch other than its repository's default one (`base.repo.default_branch`) is `elsewhere`, `{branch}`, and the plan reads and fetches nothing more, since only merges into the default branch are checked; a pull request that names no default branch fails the run before any job. It mirrors `M` and the pull request's head ref, and names the base `M` was made onto. Where `M` is a merge commit, with two parents, the base is its first parent, whatever the pull request's commits are, so they aren't listed. Where it has one parent, from a squash or a rebase, the plan lists the pull request's commits from GitHub, 100 a page and at most three pages, since GitHub lists no more than 250; listing fewer than the pull request's count of them is `couldnt-run` with `{why, listed, commits}`. Then it walks:
- n is how many of the listed commits have one parent and a diff that isn't empty. An empty commit, such as one pushed to run the checks again, has no patch-id to find, and a squash leaves no trace of it. k is how many commits, from `M` down its first-parent line and at most n of them, have one parent and a zero-context patch-id (`git log -p -U0`, then `git patch-id --stable`) that one of the n has, the walk stopping at the first that doesn't. With context, a commit replayed beside a line its new base changed would get a new patch-id.
- The base is `M~k`, or `M^1` where k is 0. A squash of more than one commit gives 0, unless its whole change is one of its commits' own, as when the rest are a change and its revert; a rebase of n commits gives n where each replay keeps its zero-context patch-id, and fewer where one doesn't, as on a file the branch renamed, which for more than one commit the next point takes. The cap at n keeps a change `main` made before the pull request, the same as one of its commits, from walking the base back.
- Where 0 < k < n, or where k is 0 and n is more than 1, the base is `M^1` only if `M`'s zero-context patch-id is that of the pull request's whole change, the diff from where its head and `M^1` meet to its head, as a squash's is; a rebase's `M` is its last replay alone. Otherwise the base can't be named, and the run is `couldnt-run` with `{why, k, n}`.
- So it is where a commit the walk counted below `M` wasn't committed in the same second as `M`, unless `M` is itself one of the listed commits, by its sha, as a fast-forward's is. That's how the walk tells a commit this merge made from one the branch had before it, such as a stacked pull request's earlier merge with the same patch, or that pull request's own commit where it was fast-forwarded: GitHub's squash and rebase merges always make commits with new shas. A rebase whose replays GitHub committed across the turn of a second is refused the same way, which errs toward can't-check. A commit of another merge into the branch in the same second as `M` would still pass for this merge's: of the 129 merged among the four repositories' last 40 closed pull requests each on November 9, 2026, the closest two in one repository merged 10 s apart.
- So it is, for any `M`, where the pull request's head merged onto the base named doesn't give `M`'s tree, with `{why, k, n, base}`, n left out for a merge commit.
- With the base named, a merge is `unchanged`, with `detail` null and no job, where it changes no file under `src/`, no dependency map of the root `package.json` (`dependencies`, `devDependencies`, `peerDependencies`, `optionalDependencies`, compared as JSON whatever their key order), and no root lockfile (`package-lock.json`, `npm-shrinkwrap.json`, `bun.lock`, `bun.lockb`, `yarn.lock`, `pnpm-lock.yaml`) but in the package's own version, which a release changes: for `package-lock.json` and `npm-shrinkwrap.json`, their `version` and `packages[""].version` aside; any change to the others counts. Otherwise `merge` gains `src`, whether the merge touches `src/`, and once the plan is whole the run writes `DIR/merge.diff`, `git diff` of `src/` from the base to `M`, before any job, for the merge check's reader; a write that fails is `couldnt-run`, with what the plan reached.

Otherwise the view runs as an open pull request's does, with `M` as its head, `M`'s tree as the merged tree each job's head checkout is checked against, and the base as named, which is also the host for connectome-host's own pull request. Each job's head clone fetches `M` itself, not the pull request's ref. `closed`, `moved` and `doesnt-merge` don't apply to it, and it doesn't read the pull request after the jobs, since a merged one can't move.

**Otherwise** it starts 12 jobs through on-gh at the harness release, each on its share of the runs, `--shard i/12`, and each on-gh polling its run every 2 s (`ON_GH_POLL_MS=2000`). Each job's setup mounts a tmpfs at `../m`, sized above the runner's memory and swap and with no inode limit, so no write there can fail for space before memory runs out, and the share doesn't start where its work directory isn't on such a tmpfs. The setup then starts the harness's pool for the share in the background, `run.ts --pair --width 3` (`WIDTH`: on the runner's 4 CPUs, with reach profiling the self-check drive, one view at each width took its slowest share's pool to 239 s at width 1, 148 s at 3 and 141 s at 4, keeping a median 1.5, 3.2 and 3.5 cores busy; four saved less than the 8 s set before the runs), which balances its share by each run's three drives (`--drives 3`): the base arm's, the head arm's and the head arm's self-check. `HOME`, `TMPDIR`, the work directory, the checkpoints, the output and Node's compile cache (`NODE_COMPILE_CACHE`, which a Node process writes as it exits, so one that starts after an earlier one of the share's has exited loads the harness's stripped files warm) are on the mount. on-gh sets up Node 24 (`--node 24`), whose type stripping runs the harness. Meanwhile the setup builds the two arms side by side: the base arm's shallow clone and install beside the head arm's blobless clone merged onto the base, then the base arm's build and pack beside the head arm's install, build and pack. Once all of an arm's packs are in, its companions' among them, it writes that arm's file in the pool's `--ready` directory by rename, holding the comma-separated pack paths. For connectome-host's own pull request, the head checkout is a blobless clone at `../connectome-head`, the same length as the base checkout's `../connectome-host`, since a host is driven from its checkout in place and a path it sees mustn't tell the arms apart; it's merged and installed beside the base checkout's install, and both ready files are empty. The setup also writes the diff of the change's `src/` from the base to the merged head, made in the head's merged checkout (the candidate's for an overlay, `../connectome-head` for a host change), as `../m/reach.diff`, or, when `git diff` fails, git's words as `../m/reach.diff.err`, before the head's ready file. The pool's head arm runs with `--reach ../m/reach.diff`, and `--reach-package` for an overlay, and the harness reads which of the two is there once the head is ready: a diff that can't be made never costs the head arm, which runs without reach. A setup that doesn't reach its end, by a failure, the head's check or merge included, or by a signal such as a cancel's, stops the pool: its process group, or, where `setsid` hasn't yet made the group, the pid it launched and then any group that pid has made since. The command waits for the pool, stopping its group if the pool's shell ends without writing a code, writes its one exit code as both arms', and brings each arm's `run.json`, `summary.md`, records, reports, `prices.json` files and views home, with the head arm's `entries.json`, `reach.json` and `reach-digests.json`, the pool's log, any `failed.json` the harness wrote and any `reach.diff.err` as `reach-diff.err`, under on-gh's size bounds: the `prices.json` files go first, since `view/` doesn't read them, then views, then the reach files, the last two drops said in the evidence (`kb`, `reach-dropped`), and a reach file that can't be copied costs that share's reach, said in `reach-uncopied`, not the job.

**It writes `DIR/manifest.json`:** `repo`, `number`, `head`, `form`, `base`, `host`, `harness` (`{repo, sha}`), `stack` where the plan chose releases, `merge` for a merged pull request's view (`{commit, k, n, src}`: k, and n where it walked, once the plan has counted them, before it checks the base they name, k being 0 for a merge commit, where no walk runs; src, whether the merge touches `src/`, once the plan has found it isn't `unchanged`), `seconds` once jobs ran, `outcome`, `detail` and `shares`, with each job's arms in `DIR/share-<i>/{before,after}/`. `seconds` is `{planned, measured?}`. `planned` is the table every share planned from: each run's and each checkpoint's base-arm seconds, as the newest manifest in `STATE/views` that kept `measured` gives them, or `null` where none did, and the shares then plan from `stack.json`'s seconds alone. `measured` is this view's own base-arm seconds, each run's and each checkpoint's longest build, kept only when every share brought its base arm home. The manifest keeps them because a posted view's shares are removed once it posts. A run that ran no job writes what its reads reached, with `shares: []`, as it does where a registry read or the harness release's check for `--forced-package` fails. A read whose failure the plan doesn't catch, or a stop that killed such a read, leaves only `repo`, `number`, `head` and a merged pull request's `merge` `commit`; a stop that killed a registry read or that check leaves what the plan had reached before it, as their failure does. A run that comes out `ran` also writes `DIR/reach.json`, unless that write fails, which leaves the manifest written and `facts` refusing the run for the missing file: every share's `reach-digests.json` joined by the harness's `reachJoined`, in `OUT/reach.json`'s shape: a share that brought none makes every line not seen to run couldn't tell, naming the share, with git's words where its diff couldn't be made, and saying so where its reach files were dropped to keep its evidence within on-gh's bounds or couldn't be copied home, and when no share brought any, or the shares' can't be joined, it's `{couldnt}` with the reason. Beside the join, `ranBy` gives, for each changed line the join says ran, the drives seen to run it, `{file: {line: [drive, …]}}`. It takes each share's digests as its drives' boots in its drives' order, as the harness writes them, so a share whose digests, those of runs with no profiled drive aside, don't number its drives' boots makes reach.json `{couldnt}` too. Each head-arm run that comes home with a `self-check/`, which the harness writes only where the self-check differs, is also copied whole, with its record, `report.txt`, `prices.json` and `view.md` where they came home, and `self-check/`, to `DIR/varied/<start>/<run>/`, where `<start>` is the run side's start in UTC as `YYYYMMDDTHHMMSSZ`. A posted view's shares are removed once it posts, and the next view into `DIR` removes them too, so this copy is what keeps the evidence of a run that varied. A copy that fails fails its share. A run removes what an earlier run left in `DIR` before it starts, an earlier `merge.diff` included, except `varied/`, which stays as long as `DIR` does.

**Exit codes and outcomes** (defined once in `run/interfaces.ts`):
- `0` `ran`: every job came home with both arms.
- `2` `couldnt-run`: a job failed (its setup, merge or install, its command, its harness, by the `why` of the `failed.json` it wrote, on-gh, or its evidence not coming home), the run side failed, it was stopped, or no harness release on this repository's `main` is named. `detail` is `{share, why}` for a job's failure, with `headNow` or `state` when the pull request moved or closed meanwhile without explaining it; `{why}` when no harness release is named, the one named isn't a commit on this repository's `main`, or the run side failed before any job; for a merged pull request, `{why, …}` when GitHub doesn't say it merged at `M` or its base can't be named (**A merged pull request**); and `{why, stopped, shares}` after a stop, `stopped` being `{signal, seconds}` and `shares` listing the jobs whose evidence isn't home. A harness failure's `why` quotes its `failed.json`'s, which the head's code could have written too, as data: one line of at most 500 characters, in a code span nothing in it can close. A usage error exits 2 with no manifest.
- `3` `arm-missing`: a job came home without an arm's `run.json`, or with the arm's harness killed by a signal. `detail` is `{share, arm, log}`, `log` being the last line of the pool's log, which the head's own code could have written. Also `3` for `closed`, `moved`, `doesnt-merge` and `needs-companion`, and for a merged pull request's `elsewhere` and `unchanged`.

**After the jobs** it reads an open pull request again. A run whose only failures are head checks explained by a push or a close becomes `moved` (with `headNow`) or `closed`. Any other failure stays `couldnt-run`.

**A stop** (SIGTERM or SIGINT) asks GitHub to cancel every job still running whose run on-gh has named, then writes `couldnt-run` with the signal and seconds as `stopped` and the shares whose evidence isn't home. The caller owns the deadline. Each job's own limit is on-gh's, 350 minutes, under GitHub's six hours for a job.

**The harness release.** `~/.local/state/context-view/harness` names the commit every view's jobs run. `run/install-harness.ts C --go D` is its only writer: it refuses a C that isn't on this repository's `main` on GitHub, asks the release gate to install `context-view-harness` at C, and writes C only once that passes. When the release that file names isn't a commit on `main`, a run starts no job and says so, as `couldnt-run`. Once the harness is rolled back past the commit that added `harness/options.json`, the run side refuses every view that forces a range. Promoting the run side's release from before it read that file runs them again only on a harness that names `forced-package` in `harness/run.ts` or `harness/lib/main.ts`, which that release greps for; on a harness from before `--forced-package`, both run sides refuse a forced view.

## view/: the view's steps and its poll

`view/view.ts`, with the `view_*.ts` modules beside it, turns a run's records into the pull request's comment, and `view/poll.ts` picks the next head to view. Both run on the house's machine, from the install, with the GitHub App's credentials. Their GitHub calls, the App's token and the escaping of an author's text come from review-workflow's `review-workflow/view` subpath, pinned to one commit in `view/package.json` and `view/bun.lock`. Moving that pin is a change here, read like any other.

**Its project.** `view/` is a Bun project of its own (`view/package.json`, `view/bun.lock`, `view/tsconfig.json`), since its pin is the house's review-workflow at one commit, and only the house can resolve it. Outside `view/`, only `workflow/`'s tests import from it, by running Bun in `view/` (`viewTs`). The view was Python until it was ported module by module, each module doing what its Python twin did, so `view_numbers.ts` does what CPython's own format, true division, `round` and `sum` do with the view's figures.

**The steps.** Each step reads one JSON object on stdin and prints one on its last line of stdout. A release's two launchers, `view/step` and `view/poll`, run `view/view.ts` and `view/poll.ts` from the release they're in, with the Bun that `ASTRA_BUN_BINARY` names, or else `~/.bun/bin/bun`, reading no `.env` file and no `bunfig.toml`, as review-workflow's launchers do, and with `--no-install`, so a module the release's `view/node_modules` lacks fails rather than going to Bun's auto-install. The poll's launcher first checks that `view/node_modules` holds review-workflow, and where it doesn't, says so and exits 2, since Bun's own exit 1 for a module it can't load would read as a pass with nothing to start:

```
view/step STEP < input.json
```

- `facts` `{dir, repo}`: reads `DIR/manifest.json`, as the run side wrote it, each share's `run.json` for both arms and its head arm's entries, for a run that `ran` `DIR/reach.json`, each list checked against what the harness's `reachOf` can give, and the pull request's title and description from GitHub. It writes `DIR/view.json`, the one file the reader, its check and `post` read. For a run that `ran`, `view.json`'s `ended` is when the run side finished, `manifest.json`'s mtime to the second in UTC, read here with the rest of the view, so a view started beside it in its directory, which removes and rewrites the manifest, can't move it before `post`. It refuses a manifest whose `harness` isn't this repository at a full commit, unless the run stopped as `moved` or `closed`, when nothing posts, or, for a merged pull request, as `elsewhere` or `unchanged`, which ran no job: each of those four gives a short `view.json`, with no arms. A merged pull request's `view.json` carries the manifest's `merge`, refused where its `commit` isn't the manifest's `head`, where a count or `src` it holds isn't a whole number or a true or false, or where it lacks what its outcome had reached: `k` and `src` for one that `ran` or came out `arm-missing` or `needs-companion`, and `k` for one `unchanged`. An `elsewhere` or `unchanged` manifest, which only a merged pull request's view writes, is refused without a `merge`. For a candidate overlaid onto the host, it fails where an arm's `candidate.versions` doesn't give a release the manifest's `stack` names for that arm, or, for a release named for one arm alone, where the other arm didn't run the lockfile's (the entry's `host`); where an `@animalabs/*` package other than connectome-host and the candidate's differs between the arms and `stack` names it in neither; and where the arms ran one version of a package with different contents. It sees only the key packages the harness records in `candidate.versions`, each at the top level of the install: a package outside them, or a nested copy of one, it doesn't see. So no difference in a key package's top-level copy that the plan didn't choose is put on the head. `view.json`'s `differing` lists each package that does differ, `{package, base, head}`, where any does. Where the manifest has `forced`, `view.json` carries it and `pack`, the candidate's package, except for a view that `moved` or `closed`, which posts nothing. The comment says after its count which ranges each arm ran the candidate past and why the view couldn't meet them, and that a difference or a failure may come from them, in a view that ran, whether or not any of its runs could be compared; an `arm-missing` view's comment doesn't say it; `facts` fails on a `forced` of another shape, an empty one, or one in a host view; a `wantedBy` is checked by its shape alone, a chosen release's `NAME@VERSION` or a package-lock key, since the view's directory holds no lockfile to look it up in, so a one-word name passes as a workspace's key would. The view knows the candidate's package by the repository's GitHub ID.
- `compared` `{dir, repo, number, head, form, base, host, harness, stack?, forced?, title, body}`: `view.json` for a change no pull request holds, such as one made to check the reader, from a harness compare run by hand. `DIR` holds the compare's two `--out` directories laid out as a view's shares, `share-<i>/{before,after}/`. From the fields given, each in the shape the run side writes it, it makes the manifest of a run that `ran` with the `share-<i>` directories there as its shares, and reads the shares as `facts` would, with `title` and `body` standing for the pull request's title and description, and `DIR/reach.json` where there is one, as the harness's `reachJoined` writes from the shares' `reach-digests.json`; without one, the comment has no reach paragraph. It writes the manifest as `DIR/manifest.json`, then `DIR/view.json` last, so a manifest that can't be written leaves no view. It asks GitHub nothing, so it refuses a repository outside the four by its name, not its ID. It refuses a `DIR` that isn't a directory, then removes what an earlier view wrote there, its `view.json`, `manifest.json`, `reader.json` and the comment's parts, before any other check, so whether it writes this view or refuses, none of those files predates it. The workflow reads what it writes only in a dry view, since its head is in no pull request.
- `post` `{dir, reader?, reads?, post?}`: posts the view's comment, one per head, in as many parts as GitHub's 65,536-character limit takes. Every word in it is fixed in `view.ts`, `view_numbers.ts`, `view_reach.ts`, `view_read.ts`, `view_usage.ts`, `view_words.ts` and the files the pinned review-workflow's `COMMENT_FILES` names, taken from the run's manifest and records, or a head GitHub names (the pull request's head now, and the head a kept comment was first posted at), apart from the reader's account. Where the records differ and no reader ran, as for an automatic view, the comment says so in fixed words, says that a view asked for with `/context-deltas` gives an account of the records of the head as it is when that view runs, and names in a fold the runs whose records differ; since the reader's sources, and with them the pull request's title and description, are part of the result only where a reader ran, such a view never keeps a comment that has an account. At the same head, `post` would replace an account, as it replaces any comment of that head with another result; what spares one is the poll's order: no automatic view starts at a head any house view ran at, an ask's included, and an ask waits for an unsettled view of its head before it starts. The paragraph after its first line links `CHECKS.md` at the harness commit the view used. After the sentence on the runs' records, whether or not they differ, and the line naming any releases the arms ran differently, a paragraph says which of the change's source lines ran in no profiled drive, which files no profiled host loaded and which deletions no profiled drive reached, or that everything that could run did, and what it couldn't tell and why, in `CHECKS.md`'s words; a list longer than about three lines of the comment, or a reason longer than that, is cut, saying how much it leaves out, though a list's first item always prints whole. Whenever the paragraph cuts a list or a reason, or counts lines or deletions it doesn't name, a fold below the comment holds, file by file, every changed line and deletion not seen to run, with each reason for a line or deletion it couldn't tell, whole unless it's longer than a comment can hold, and the paragraph's last sentence points to it. The comment never points its reader at `view.json`, which only the house can open. A later head with the same result keeps the comment and edits its first line. A posting that fails partway deletes the parts of its comment the pull request then lists, and says what became of them, a delete GitHub refused included. With `post: false` it posts nothing and writes the comment beside `view.json`. It posts nothing for a `closed` or `moved` view. Once its comment is on the pull request, posted, edited or kept, a view that could tell wants the pull request's project field `Changes context` through review-workflow's installed `~/.local/bin/review-poll want --kind context`, whose `statuses` step sets it: Yes where the records of some run it could compare differ, No where it compared runs, every one, and none differ, by the comment's own headline. So No means none of the view's runs differ, and a change on a path no run reaches reads No. The want is timed at `view.json`'s `ended`, so of two views of a pull request the one whose run side finished later stands, to the second, whichever posted first; a `view.json` without `ended`, as one `facts` wrote before it carried it, wants nothing and says so on stderr. A dry view, one that moved or closed, one that couldn't tell and a merged pull request's view want nothing, and a want that fails is said on stderr and fails nothing.
- `stopped` `{repo, number, head, post?}`: posts the stopped words for a head whose run failed: one line saying the view stopped, and a link to `CHECKS.md` on `main`. It posts nothing if a whole view of that head is already there, or if the head has moved or the pull request has closed.

**Exit codes:** `0` with the answer on the last line. `1` with why on stderr's last line, cut at its end to 1,500 characters, since the workflow keeps a step's last 1,500 characters of stderr. `2` for a repository the App is installed on that the view doesn't cover, and for a command line that names no step; a repository the App isn't installed on fails at its token, with exit 1. `compared`, which asks GitHub nothing and so can't tell whether the App is installed, refuses any repository outside the four with exit 1.

**Run them from the install.** When its module is in the main working copy, `~/astra/context-view`, a step's command line refuses with exit 1 and the poll's with exit 2, each naming its installed form, since what they'd run there is whatever the copy holds, not the reviewed release. That refusal comes once their imports load: in a copy without `view/node_modules`, the step exits 1 at its import, and the poll's launcher refuses with exit 2, as above. A worktree outside the copy runs its own code.

**The poll** is a Jobs job's condition:

```
view/poll --job
```

- **What it prints:** at most one line, `{"key", "args"}`, while no view's run holds the account's runners when it lists them and neither the asks step nor the merges step has a line out with no run of it yet: again the line it printed before, while Jobs hasn't taken it and its pull request still waits, or else, where the asks step has no ask it could start, none queued on a pull request this pass lists open at a head with no unsettled view, since an ask goes first, one for the pull request whose review started first of those waiting. A line already out prints again whatever is queued, since the asks step waits for its run: holding it for an ask would leave each step waiting on the other. An ask on a pull request the pass doesn't list open holds nothing, since the asks step can't serve it either (Oscar-1005, room-203 #414714), and nor does one whose head has a view that hasn't settled, which the asks step passes over until that view settles. The listing isn't a lock, so a view started by hand between it and Jobs' start runs beside the one Jobs starts. `args` is `{repo, number, head, auto: true}`, the step input the workflow starts with, `auto` marking a view no one asked for. A view's run holds the runners while it's unsettled and its run side hasn't written `manifest.json` in its directory (`viewDir()`) since the run began; the run side writes it once its jobs have ended, or, for a view that's stopped, once it has asked on-gh to stop them, so a view whose reader is reading holds none. A stop on-gh can't confirm, whose exit is in the share's `on-gh.stop`, can leave a job on the runners that no step sees (`holds()`; Oscar-1005, room-203 #413364, #413376). A run whose directory the poll can't name, a dry view's among them, holds them until it settles. The listing, `astra-workflows runs --record` of `workflow:context-view` and of `workflow:context-view-merged`, holds every run of either record whoever started it, so any start of either holds the runners as above, and a pass that waits for them names on stderr each run that holds them, a colleague's start from a session as "a session's start under" the key it was started under. The view and merge keys are the house's: a start from a session with `workflow_run` holds the runners until it settles and never counts as a head's view, a merge's check or a line's run, whatever its key (acorn-2240). So where its head waits on a review, the poll views that head again once it settles, in the same directory (`viewDir()`), which replaces what a posting view started from a session wrote there: read that first. A view meant to count is started with `astra-workflows start --record workflow:context-view`, under a key beginning `context-view/`. A head's view run again goes under the head's view key, the part before any `:`, with `:again-<n>` after it, which `holds()` reads as the poll's own until its manifest, and which counts as that head's view; an ask's or a retry's key with `:again-<n>` after it is no view key, so its run holds the runners until it settles. A dry view started that way goes under a key of its own whose part before any `:` isn't a view key, such as `context-view/readback:…`, and holds the runners until it settles: a view key there would put that head in `seen`, so the poll wouldn't view it itself. From a session, any key does. One view's runners at a time across the steps is a concurrency cap under nissa's rule that a cap is back-calculated from measured limits (personal:petra-625 #270969, #270988; Oscar-1808, room-203 #413173). Its basis was measured over Nov 2–9, 2026 from GitHub's records of every Actions job on nissa-seru's account and on-gh's receipts (Prudence-2217, room-203 #413287):
  - the account ran at most 40 jobs at once, and jobs waited for a runner only while about 40 ran;
  - a view takes 12 jobs (`--shard i/12`);
  - everything else peaked at 38, xpkg alone, and held more than 28 runners for 5 minutes of the 174 hours and more than 16 for 50 minutes.

  So one view beside them leaves xpkg's merge checks waiting on views about 5 minutes a week, and a second would make it about 50. Counting only a view's runners frees the slot during its reader: of 74 views that compared, the run side took a median 221 s (p90 308 s), and the reader ran in 29, a median 43% of each of those, up to 587 s. On the same 8 days of review starts replayed 2,000 times, the worst wait falls from 210 to 135 minutes and the mean from 27 to 15, and at most 2 readers ran at once in the median replay (4 in the worst), beside the 315 Sol calls the house has run at once (two pr-review runs, Nov 5).
- **Which pull requests:** a pull request in a covered repository waits for a view once a review of it starts, as review-workflow's poll starts one for an opening, a reopening, a mark as ready or a maintainer's `/review` (Oscar-1005, room-203 #413015, for nissa's personal:oscar-1808 #412908). The poll reads those starts from the workflows store, the runs under `pr-review/open:` and `pr-review/ask:` (`REVIEWS`), so the review poll's rule decides, with no copy of it here; any other review (a release's, a pull request's before it opens, a restart) starts none. A pass with no `reviews` in its state counts every review the store holds and starts nothing for them, and a review in a covered repository the pass doesn't list waits uncounted until one does. A pass reads the review starts before it lists the open pull requests, so a start it counts is of a pull request open before the listing. A pull request keeps the place of its first review start while it waits. Review starts are matched to the listing by repository name, and a head's `view.json` is read under the name the listing gives, so after a covered repository is renamed, a start made under its old name and not yet counted, or a `needs-companion` head reviewed again at that head, gets no automatic view until its pull request's next review start, such as a `/review`, a reopening or a mark as ready, since a push starts no review; `/context-deltas` still asks for one at any time (Oscar-1005, room-203 #417204; Cordelia-2434, #417262).
- **Which head:** its head as the open-pull-requests listing gives it when the line prints, so a pull request that moved while waiting is viewed at its newest head. A pull request stays queued until a view has run at the head it has: while any view of its head is unsettled, an ask's included, it stays and isn't waiting, and once a view of the head settles after its line was taken, it leaves. So a push during a view's runs, which ends that view `moved` and posting nothing, gives the new head a view after it, in the place of the first start, once the old view's runners are done. The old poll viewed each new head; this one views only where a review started, so without that a pushed pull request would get no view until its next review (Cordelia-2434, room-203 #413401, #413627; Oscar-1005, #413418, #413633). A new review start at a head whose turn was taken, during its view or after it, lets that head wait again, so a `needs-companion` head is viewed again at its next review. A head whose view has run, an ask's view included, isn't viewed again while its pull request stays open (`seen`, or the run while the store keeps it), unless that view's `view.json` (`viewDir()`, the directory the workflow keeps a posting view in) says `needs-companion`: no stack of releases could run its arms, which is the releases' state, so its next review views it again (#413022). A `view.json` that's there but can't be read is said on stderr and counts as `needs-companion`, so a damaged file costs a view rather than losing one. That retry runs under its own key, the view key with `:review-<run>` after it, naming the review start that queued it: the workflows store answers a start under a key it already holds with that run and starts nothing, so the bare key would start no view for the week the store keeps the first (Cordelia-2434, #414360). A draft waits until it's marked ready, and a closed pull request leaves the queue.
- **Newcomers:** a pull request whose author is new to the repository, outside the review poll's `KNOWN` (owner, member, collaborator, contributor), waits for its view from a review start as any other does (nissa, personal:abigail-2459 #448069, reversing ask-467's hold). So its code runs on `nissa-seru/runs` as her GitHub account with no maintainer's say, though GitHub itself holds back a first-time contributor's own workflow runs: `run.yml` starts only on `workflow_dispatch`, declares `permissions: {}` and names no secrets, so no token, secret or write access reaches that code, and it can use her runners for up to 12 jobs of up to 350 minutes a view. A newcomer's review start that a release before this one passed over stays counted, so its pull request waits for its next review start.
- **Exits:** `0` with a line, `1` with none, `2` on a failure, said on stderr.
- **State:** `~/.local/state/context-view/poll.json`, under its own lock, the views' line under `views_line`. The release before this one is the Python twin, and a job's pass of each, over the same state, writes the same file and gives the same cursor, byte for byte (room-203 #460313), so the way back reads what that release would have written. `line` stays `null`, and each repository's stored listing keeps its pull requests' authors' associations, which nothing here reads, for the releases older still, which wait on `line` and pass over a newcomer by them. Jobs' cursor says which line it took.
- **Without `--job`,** as when it's run by hand to check it, a pass prints what it would and changes nothing: it keeps no line, queue or `seen`, gives no cursor and puts no 👀 on a comment. A line is out only because a job will take it, so only a job's pass puts one out.

**Its asks step** is another job's condition, a view of a pull request asked for by a comment:

```
view/poll asks --job
```

- **An ask:** a comment on a pull request in a covered repository whose text, leading blank lines aside, starts with a line holding `/context-deltas` alone, by an account in `view_words.ts`' `ASKERS` that GitHub gives write access, and not the App's own. A repository's first pass starts from then, so no comment before it asks. A permission GitHub doesn't answer fails the pass, so the comment is read again.
- **What it prints:** a line in the views' poll's shape, under the same rule of one view's runners at a time, for each ask in the order the asks were made: `args` is `{repo, number, head}`, with no `auto`, since the view was asked for, its head the pull request's head as GitHub gives it in the pass that prints the line, and the key is that head's view key with `:ask-<comment id>` after it, so an earlier view of that head doesn't stand in for the ask. A newer ask on a pull request takes the place of one still queued there, and of its line where that's out and not yet taken.
- **👀:** each ask queued gets it, meaning a view is coming, unless GitHub refuses it or the call fails, which is said on stderr. An ask leaves the queue once Jobs takes its line. A start that fails leaves Jobs' cursor where it was, so the line prints again.
- **An ask that waits or goes:** one whose repository a pass doesn't list, or whose pull request GitHub doesn't answer for when its line would print, waits, said on stderr, and the next ask prints in its place; a pull request GitHub doesn't answer for as its ask is taken in fails the pass, so the comment is read again. One whose head has a view that hasn't settled, an automatic view or another ask's, waits for it, said on stderr, and the next ask prints in its place: two runs of one head would share its directory (`viewDir()`), each removing the other's evidence, and a view whose runners are done may still be reading. One whose pull request is closed, or that GitHub has no pull request for, is said on stderr and gets no view. A push before its view's runs finish ends the view as `moved`, posting nothing; one after them still posts the view of the head its line named, saying the pull request's head has since moved. Asking again views the new head.
- **All three steps:** a line any of them has printed holds the other two until a house run under its key shows in the workflows store, so one view's runners at a time holds across the three jobs. A paused job's line holds the other steps until the job resumes and takes it, and so does the line of a job held after a start whose effect isn't known, until its filer resolves it; a start refused with nothing done ends that occurrence, and the next prints the line again (Fern-2426, room-203 #414504). So pausing or holding the views job holds nissa's asks behind its line, and an asks pass says on stderr which line it waits on once no view holds the runners. Pausing or holding the asks job, with an ask it could start queued, holds new automatic views the same way, until it resumes; a views line already out still prints. Pausing or holding the merges job with its line out holds both others the same way. The merges step goes by the count of pull requests the views step's last job pass left waiting, so pausing or holding the views job while any wait holds merges until it resumes (Prudence-2217, room-203 #417796). Two views' runners never run at once, but for a view started by hand between a pass's listing and Jobs' start, a view run from a copy of the workflow's script rather than from either record, which no listing by record shows, and a job a stop on-gh couldn't confirm left running, as above (Oscar-1005, #414714).
- **Why a step's line ends at its own next pass after Jobs takes it:** by then that line's run is in the store, unless its job stays paused, before its next condition, past the week the store keeps a settled run. Jobs adopts a condition's cursor only once its action succeeds, or once whoever holds an action whose effect was unknown confirms, with evidence, that it took effect (astra-jobs' `adoptFrozen`, reached from the success branch in `src/store/outcomes.ts` and from `effect_confirmed` in `src/store/control.ts`), and the workflow action succeeds only once `startHouse` has made its runs (workflow-house's `src/provider.ts`). A job runs one occurrence at a time, so its next condition comes after.
- **State:** the `asks` part of the same file, with its own line and queue. Each step reads the others' lines, the views and merges steps read the asks' queue, as above, and all three use the App's tokens. Its job's own cursor says which line it took.

**Its merges step** is a third job's condition, a check of what a merged pull request merged (workflow:context-view-merged):

```
view/poll merges --job
```

- **A merge:** a pull request in a covered repository that GitHub gives as merged, into any branch, from 2026-11-09T10:57:53Z (`SINCE`, the merge of membrane's #248) on. A pass lists each repository's closed pull requests last updated first, page by page until a page ends before the repository's place, since a merge's last update is no earlier than the merge. A first page unchanged since the last listing, by its ETag, holds no newer merge, so the merges that listing found stand.
- **What it prints:** a line in the views' poll's shape for the oldest merge past its repository's place with no run of its own in the store, under the same rule of one view's runners at a time. `args` is `{repo, number, merged}`, `merged` being the merge commit GitHub gives, and the key is `context-view/<repo id>#<number>@merged:<merge commit>`. A merge whose key a house run in the store holds, with or without an `:again-<n>` after it, as a check run again by hand with `astra-workflows start` has, isn't printed. A merge into a branch other than the repository's default one, or one the run side finds `unchanged`, still prints, and the run side's `--merged` says so in its manifest.
- **Last in the slot:** it prints nothing while an ask the asks step could start is queued (`asksFirst()`, the views step's own test), or while the views step's last job pass left a pull request waiting, or before any views job pass has counted them, as on a first pass whose state holds no `views_waiting`. The Python release before this one writes `views_waiting` as this one does, so its count stands here. A line already out prints again whichever of these waits, since the other steps wait for its run, under its repository's name in this pass's listing; one whose repository the pass doesn't list is dropped, as the views' line is, and its merge prints again once the repository is listed, since its place hasn't moved.
- **Its place:** each repository's, by its GitHub ID: `since`, the `merged_at` of the last merge it moved past, and `handled`, the numbers moved past at that second. It moves past a merge once Jobs takes its line, or once a house run of it that another start made, such as a check run again by hand with `astra-workflows start`, is in the store and no earlier merge in its repository waits, so a merge isn't checked again after the store clears its run a week later (Prudence-2217, room-203 #419144). A repository a pass doesn't list keeps its place.
- **Its runners:** a merge check holds them while it's unsettled and its run side hasn't written `manifest.json` since it began in its own directory, `merged.<owner>.<repo>.<number>.<the merge commit's first 12>` under the views' directory (`mergeDir()`), apart from any head's view.
- **State:** the `merges` part of the same file, with its own line, places and listings. Neither other step writes it. The release before this one, the Python twin, reads and writes it as this one does, so the way back keeps the merges job.

**The build.** The promote's `prepare` runs `bash view/build.sh STAGE`. It installs `STAGE/view/node_modules` from `bun.lock` with the Bun the launchers run, `bun install --frozen-lockfile --production --ignore-scripts --backend=copyfile`: no development dependency is installed, no package's install script runs, and every file is a copy, as the promote's own install makes them. Then, before anything switches to the release, it runs each launcher with `--help` from the stage, and refuses if a file in the stage names the stage's path, or a symbolic link in it points into that path, since the release is moved into place once it's built. The path check comes after the loads, so it also sees a file a dependency writes into its own directory when it's first loaded.
